# Operations and recovery

## Storage and spending controls

Photo storage is capped in application code at 8 GB total and 250 MB per member (decimal bytes). Actual processed bytes are reserved atomically before R2 writes; pending uploads and deletion backlogs remain charged. Cleanup releases capacity only after confirmed object deletion. Existing objects are conservatively charged the maximum upload size during migration. The counter must equal `SUM(stored_object.bytes)`; investigate discrepancies before enabling uploads. Do not upload objects outside the application or lower the ledger to bypass a quota.

These limits are not a Cloudflare account-wide spending cap. Other buckets, direct operator writes, R2 operations, and provider plan changes are outside them. Processing budgets allow five attempts/member/day, 150 attempts/day across the app, and 3,500 reserved transformation units/month. A new post or avatar reserves two units for its two sizes, and legacy-thumbnail conversion reserves one. Small posts and avatars reuse a single object but keep their conservative two-unit reservation. Both stored variants count against byte limits and are included in backups. Backups are local encrypted files, adding no hosted backup storage or idle service. Do not enable paid plans automatically.

Cleanup runs every 15 minutes. Each invocation processes one account (five posts and up to 100 rows per ancillary table), two avatar objects, and two post objects. It also attempts one legacy grid-thumbnail conversion within the same budgets; failed conversions keep their full-image fallback and are not automatically retried while their attempt record is retained (60 days). It also prunes bounded batches of expired sessions, email-link records, email budgets, and old processing attempts. Backlogs preserve privacy and remain charged to quota; inspect them if storage is unexpectedly full. Account content cleanup completion does not imply every queued R2 object has been physically deleted.

Private image delivery also uses an ephemeral, named Workers cache with one-hour freshness, separate from R2 storage accounting and backups. Authorization and current object selection always precede lookup, so deletion and access changes deny new reads even while bytes remain internally cached. Freshness expiry is not a physical-erasure guarantee from the provider. Never overwrite an existing immutable object key during repairs; use a new key and update its authorized reference. Maintenance denies media before lookup. Recovery must reconcile deletion state before reopening, as usual. Code rollback can simply resume direct R2 delivery; no cache purge is required for privacy. See [private delivery](../src/server/photos/README.md#private-delivery) for failure behavior and telemetry.

## Backup creation and retention

Use a private directory outside the repository, a random 32-byte key in a separate mode-600 file, and a new output filename each time:

```sh
node scripts/ops/backup.mjs /private/path/slowmass-YYYY-MM-DD.enc /private/path/backup.key
node scripts/ops/restore-check.mjs /private/path/slowmass-YYYY-MM-DD.enc /private/path/backup.key
```

The backup includes a D1 SQL export, referenced published post/avatar bytes, checksums, and a capture timestamp. Missing media causes failure. It is an application snapshot, not an atomic transaction spanning D1/R2: if concurrent deletion removes a referenced object, retry after the operation settles. Encrypted archives and keys must not enter the public repository. Plaintext temporary directories are mode 700 and removed after the command finishes; archives are mode 600. A killed process may require removing its private temporary directory manually.

Current operation is **manual**: take a backup daily while people are using the app and before manual migrations or recovery work. Routine code-only deployments and reviewed backward-compatible automatic migrations use this existing cadence; automatic migrations additionally record a D1 Time Travel bookmark before applying. This bookmark does not contain photos and does not replace encrypted off-device backups. Verify it, then copy it off this Mac. Keep archives no more than seven days, replacing the oldest only after a newer verified copy exists; manually delete expired copies from the Mac and Google Drive, including Drive trash. A recovery kit containing both an archive and its key is sensitive as a whole—keep its Drive access private. No automatic local schedule or Drive upload has been configured. The requested handoff is a clearly named ZIP for the owner to copy.

The latest verified snapshot defines recoverable data. With daily successful copies, the target is at most 24 hours of lost new content; a missed backup extends that window. This is a target, not a verified recovery-time guarantee. D1 Time Travel provides an additional provider-managed recovery path, not an R2 backup.

## Recovery without resurrecting deleted content

1. Enable `MAINTENANCE_MODE=true` in a deployment before any recovery. API and media access return 503 and scheduled mutation work stops. Keep the site closed throughout reconciliation.
2. Preserve a fresh copy of the current database and deletion decisions if available. A stale snapshot cannot tell you about later deletions, removed followers, or blocks. Use the newest authoritative records, not an older backup's membership state.
3. Run the encrypted restore checker. It verifies ciphertext authentication, SQL integrity/foreign keys, and every photo checksum in disposable local storage. It clears sessions, pending email links, invitation join credentials and retry payloads, push subscriptions and queued deliveries, and disables active memberships in the restored copy. It never modifies production. Repeat these quarantine steps on any actual restored database before reconciling access; invitation credentials do not depend on the auth secret and must be cleared explicitly.
4. Restore into isolated resources first. Reapply current account, post, and comment deletion records, avatar removals, and follow/block decisions. Queue removed objects; preserve invitation IDs, ancestry, and issuance/join times. Rebuild the byte ledger from objects actually retained and include cleanup reservations. Do not simply restore old `storage_budget` values into a bucket containing different objects.
5. Validate permissions, object checksums, invitation provenance, and cleanup through API/database checks. If current deletion/access decisions cannot be recovered, keep affected accounts disabled; do not silently reactivate them from an old snapshot. Keep expired sessions invalid and use a fresh auth secret if restoring after credential loss.
6. Only reopen accounts whose current access state has been reconciled. Remove maintenance mode in an explicit deployment after validation. The restore checker is deliberately not a one-command production overwrite tool.

The automated exercise verifies an encrypted synthetic SQL/photo archive and rejects tampered ciphertext. The initial production archive contains no photos, so its successful restore establishes database recovery only; synthetic fixtures establish the media path. On October 10, 2026, a disposable hosted D1 database was written with a synthetic value, bookmarked, changed, and restored to that bookmark. A subsequent query returned the original value. The disposable database was then deleted; production was not restored. A complete application cutover after disaster remains an operator procedure, not an automated guarantee.

On October 11, before migration 0011, a fresh encrypted production archive passed quarantined local restoration, SQL integrity checks, and checksum verification for two stored images. Sessions were cleared and memberships disabled only in the disposable restored copy; production was not restored. The owner confirmed copying the initial recovery kit off-device; fresh backups still require manual off-device copying.

## Release and rollback

Run `npm run check` before deployment. Routine backward-compatible migrations classified as `automatic` are applied by the production job before deploying dependent code, using the existing backup cadence and a recorded D1 Time Travel bookmark. For manual schema/data migrations or recovery, create and verify a fresh encrypted backup and follow the required maintenance sequence. Review compatibility with the previous Worker before classifying a migration as automatic; SQL is not automatically analyzed for safety. For storage-ledger initialization, deploy the checked code in maintenance mode first, allow existing requests to drain, apply migrations, and redeploy without maintenance. Trigger migrations may require the documented atomic file-import workaround; include their `d1_migrations` entries in the same import. Never edit an applied migration.

Prefer code rollback with forward-compatible schema. Do not roll back to code that permits unmetered uploads after enabling storage limits, or that ignores deleted memberships. Maintain the maintenance gate if correctness is uncertain. Pushes to `main` use the checked, serialized GitHub production deployment described in [setup](setup.md#production-deployment). Before maintenance, manual migrations, recovery, or manual rollback, set `AUTO_DEPLOY_DISABLED=true` in repository variables, let active deployments finish, and cancel queued releases. Automatic deployments reject unknown history, unclassified migrations and pending manual migrations before changing the database. A failed migration stops the release, preserving earlier successful migrations; reruns resume from history. After migration success, a failed Worker deployment leaves the expanded schema in place. Never automatically reverse migrations or restore the database over intervening writes. The job verifies complete migration history before publishing and never rolls back a failed release automatically. Resume only after the latest `main` code is compatible with production.

## Web Push operations

Opt-in delivery uses the existing Worker and D1. The hourly cron adds 24 scheduled invocations/day, plus opportunistic dispatch after relationship/interaction mutations and avatar completion. Quarter-hour maintenance remains separate. Each pass claims at most five deliveries and performs indexed bounded cleanup. An idle backlog drains at most five deliveries per hour. Like bursts coalesce per device/event with a ten-second eligibility delay, so new likes and retries can wait for the next hourly pass unless another mutation dispatches them first; larger backlogs can take longer. Per-notification retries stop after eight attempts or 24 hours; provider TTL is one hour. This avoids unbounded provider calls but does not guarantee instant delivery; inspect backlog and Worker CPU/error metrics as opt-ins grow. No paid plan or hosted queue is enabled.

Safe aggregate inspection: `SELECT COUNT(*) AS pending, MIN(created_at) AS oldest, MAX(attempts) AS attempts FROM push_delivery;` and `SELECT COUNT(*) AS devices FROM push_subscription;`. Do not print endpoints, browser encryption keys, payloads, or VAPID credentials in logs. Provider 404/410 prunes dead subscriptions; auth cleanup removes expired sessions and their subscriptions. `push.send_failed` records only error type, and dispatcher failures carry no content.

Maintenance mode stops push dispatch. Scheduled handlers ignore unrecognized cron expressions, including obsolete schedules during propagation. For rollback, restore the delivery cron expected by the matching Worker; a minute-based dispatcher will not recognize the hourly expression. Remove the delivery cron before running a version that treats every scheduled event as general maintenance. Committed delivery intents can safely expire while dispatch is disabled. Restored databases must explicitly clear both push tables before reopening: never replay stale alerts or recover old device credentials from backup. Preserve the VAPID key file separately and privately; it is not included in D1 backups. Alerts already accepted by providers cannot be recalled; generic text limits disclosure, and destinations reauthorize. Read acknowledgements dismiss local alerts only, not delivered alerts on other devices.
