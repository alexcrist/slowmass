# Architecture and operating model

Status: proposed design. Provider documentation reviewed October 10, 2026; account-level behavior and selected dependency versions must be verified during the first implementation stage.

## Purpose

Give people control over their attention and private social connections. The product serves relationships rather than engagement metrics: chronological feeds of own posts and accepted follows, finite pages, explicit consent to follow, no advertising or behavioral tracking. Cost decisions should preserve that purpose.

## Initial stack

One TypeScript application: React/Vite mobile-first client, Hono API on Cloudflare Workers, D1 relational database, private R2 object storage. Serve static assets and API from the same origin. Use Better Auth with one-time email links and D1, validating the supported adapter and migration workflow in a spike. Choose pinned supported versions during implementation, not from memory. Use a single package initially rather than a monorepo toolchain.

Proposed source layout: `src/client/features/`, `src/server/features/`, `src/shared/` for cross-boundary schemas only, and feature-independent infrastructure alongside server features. Migrations live in `migrations/`. Keep domain SQL in feature-owned stores; do not add a generic persistence framework. Auth library tables have one clearly owned migration stream integrated with application migrations.

Build the frontend as static assets; private feeds have no SEO need and do not require per-request server rendering. No Redis, realtime service, dedicated queue, analytics vendor, or always-on VM at launch. Use local Workers/D1/R2 emulation for development and a separate disposable test environment when remote verification is required.

## Core data and concurrency

Concepts: user/profile, session/account (auth library), membership with immutable inviter attribution, invitation, follow request/accepted relationship, block, media upload, post, like, comment, notification, and cleanup task. Database uniqueness enforces one relationship and one like per pair; foreign keys and explicit lifecycle rules prevent dangling accessible content.

Use validated client UUIDs for retryable posts/comments and server timestamps. Make publish, follow transitions, and notification creation retry-safe with scoped idempotency keys or natural unique constraints. Use D1-supported atomic batches/conditional SQL, not assumptions about interactive transactions. Check permissions in the mutation's SQL/atomic operation where a preceding check could race with removal or blocking.

Notifications use an indexed directory of interaction sources maintained by database triggers in the same transaction as the source mutation. This was introduced after a local 3,000-post benchmark showed lifetime aggregation reading 216,000 rows to display and acknowledge 20 events. The indexed version read 320 rows for that workload in the October 11 benchmark, before acknowledgement tracking was removed. Reads still evaluate current membership, blocks, publication state, and visible like-group ordering; the index grants no access. Since migration 0029, the like trigger assigns each like to a timeline-ordered group when it is written, so list, badge, acknowledgement, and focus queries keep grouping by event key unchanged. Activity remains one chronological list. Migration 0018 adds per-source read receipts with monotonically increasing versions and an index of unread sources. Page reads are read-only; a separate authenticated acknowledgement validates the displayed version and clears only visible sources through that version. Badge reads seek unread sources rather than scanning read history. Legacy read markers are imported once, and source deletion cascades to receipts. Logical event keys and versions are shared by the list, badge, and acknowledgements, and identify Web Push deliveries. Migration 0019 adds an opt-in subscription and transactional delivery queue using the same identities. A bounded dispatcher runs after interactions and on an hourly cron in the existing Worker, with leases and bounded retries. Likes do not send push alerts (migration 0029); failed immediate deliveries wait for another dispatch opportunity; an idle backlog drains at most five deliveries per hour. Generic encrypted payloads avoid lock-screen disclosure, and current authorization is checked before sending and on opening Activity. Migration 0020 adds follower events after acceptance or invitation photo completion, atomically preserving existing receipt versions and pending deliveries without backfilling old accepted follows. Follower visibility additionally requires the live accepted relationship and completed profiles. No new hosted service is introduced. See the notifications and push READMEs for tradeoffs and limits.

## Authorization and sessions

Same-origin secure HTTP-only cookies; use the auth library for single-use email verification, hashed link tokens, CSRF defenses, session expiration, and logout. Validate trusted origins and invitation eligibility at the backend, including email verification/account creation. Never treat an unverified email or client-supplied user ID as identity. Do not fetch avatars from third-party identity services.

A viewer can access a post only as its owner or through a current accepted follow, subject to blocks and deletion. Reuse this predicate for feeds, detail views, media, likes, comments, and notifications. Notification ownership alone never grants access to its target.

Profile usernames, names, and avatars are visible to active signed-in members unless either member blocked the other. Bios, posts, and Following/Followers lists require ownership or an accepted follow. Relationship pages recheck access and filter accounts blocked in either direction with the viewer before pagination; requests and blocked-account lists remain owner-only. Avatar media remains in private R2 and every request checks membership and blocks.

Private media is served through an authenticated Worker route with a resource ID and allowlisted variant. R2 public access stays disabled. Every request rechecks authorization, including conditional requests. By the owner's October 24, 2026 decision, post photos, whose URLs never change bytes, use `private, max-age=604800, immutable`: a device may show a post photo it already downloaded for up to seven days without asking again, even after deletion, follower removal, or blocking. Avatars and event covers reuse URLs across replacement, so they use `private, no-cache` with a key-derived ETag: the device keeps bytes but every use is reauthorized, and a matching validator returns 304 without an R2 read. Event-link previews remain `private, no-store`. Private content is never cached by a service worker. The implemented [private delivery module](../src/server/photos/README.md#private-delivery) reuses immutable processed bytes in a named Workers cache only after fresh authorization selects the current object key. Internal entries expire after seven days; access revocation and avatar replacement do not depend on expiry or global purge. No public cache route or cached authorization decision is introduced. Signed-link delivery remains a future tradeoff.

Membership retains a permanent parent pointer to the inviter and the accepted invitation. D1 triggers atomically consume invitations and reject changes to provenance. Issuance and acceptance require an active inviter. The single bootstrap root is protected by a unique index. Preserve minimal tombstones through account deletion; do not build mass-ban tools yet.

Members invite people by texting an invite link or an event link. Each member has one invite link, `/#invite/<token>`: a 48-character credential in the fragment, stored as a hash with recoverable ciphertext, valid for seven days from the owner’s latest dialog request, and replaced in place by a new version once it expires or is revoked. Refreshing an unexpired link preserves its credential/version and pending email claims; the guarded update cannot shorten expiry or revive a revoked version. Signed out, it reveals only whether it admits new people. Signing in through it binds a short-lived email claim to the exact link version; verification atomically creates a shared invitation from the link's owner recording that version, plus the membership. Every join therefore records its source: the root, a legacy email invitation, an invite-link version, or an event-link version. An operator can count joins per source and disable a burst of bot sign-ups with the [operations runbook](operations.md#join-sources-and-shutting-down-bot-sign-ups); there is deliberately no in-app moderation tool. Personal email invitations were removed in October 2026; their records remain. See [Events](#events) below.

An initial-profile trigger creates mutual accepted follows between a former personal-invitation inviter and invitee once both profiles exist. It checks active membership and blocks in the same transaction, does not run on profile edits or sign-in, and does not backfill completed profiles. Invite and event links create no follows.

Email delivery uses Amazon SES in `us-west-2` on à-la-carte pricing, without tracking pixels or link tracking. Better Auth stores one-time tokens hashed and rate-limits requests through D1. The application limits each recipient to three sign-in emails per hour but has no application-wide daily cap. Total spending is bounded outside the app: an AWS Budgets action denies the sending user at $100 of SES charges per month, and SES's own sending quota limits the worst case to roughly $5 per day. Budget data lags actual usage by hours, so the cap is approximate, and reaching it stops all sign-in email until the next month or a manual reversal. See [SES setup](setup.md#amazon-ses).

The Worker signs SES requests with a maintained SigV4 library using an IAM user that may only send from the configured address. SES has no idempotency key, so the transport never retries; a lost response returns a failure to the member, and requesting another link can deliver a second copy of an equivalent single-use link. Notification email is chosen per category in Settings; by default only event update blasts, cancellations and co-host invitations are emailed, since answering an event is treated as agreeing to hear from its hosts and an invitation needs an answer. Each email goes to one recipient with a category-specific unsubscribe link and RFC 8058 one-click header. It never consumes the sign-in budget; separate daily caps (30 per member, 5,000 overall, about $15/month at most) keep it from exhausting SES quota or the budget cap that sign-in mail shares. See the [notifications README](../src/server/features/notifications/README.md). Combining several providers is rejected because the extra failure modes and data processors cost more than they save.

## Photo lifecycle

Client resizing improves upload speed but is not validation. Accept bounded uploads from authenticated eligible users, enforce per-user quotas, and reject oversized bodies while streaming. Restrict input formats to still formats verified by the processor; reject animation and SVG. Handle phone orientation and unsupported HEIC explicitly.

Use the Cloudflare Images binding to inspect/decode/re-encode private bytes and generate bounded WebP variants per post (1600px full and 480px grid, reusing the processed full image for small posts) or avatar (320px small and 1600px large, sharing the object for small inputs) at upload, storing the result in R2. Set pixel limits, output dimensions/quality, and metadata stripping explicitly. Retain no original after successful processing. Never resize on each view. Verify binding availability, remote test support, format detection, metadata removal, CPU usage, and free-tier accounting before committing to this path.

Lifecycle: reserve an upload record and idempotency key, process into private temporary/final objects, then atomically publish the post only after required variants exist. Publication retries return the same post. Processing errors expose no post or original and can be retried. A scheduled bounded cleanup pass removes expired uploads and retries deletion tasks. D1 and R2 cannot commit together, so write durable intent and reconcile orphan objects; do not imply distributed transactions exist.

If the image binding cannot meet the free-tier/runtime requirements, stop that implementation stage and document a concrete alternative and its cost. Do not silently replace trusted processing with client-only checks or publish raw originals.

## Feed and pagination

Query the viewer’s own published posts and current accepted follows in descending `(published_at, id)` order. Include the viewer directly in the eligible author set without creating a self-follow; each author contributes the same bounded number of candidates. Use a validated cursor with a bounded page size and an upper snapshot boundary so newer inserts do not shift an ongoing pagination session. Preserve cursor history for Newer/Older navigation; a refresh starts a new snapshot. Current access and deletion always override the snapshot.

Index actual query patterns and inspect query plans/rows scanned. Batch aggregate like/comment counts and viewer-like state per page. Avoid one query per card. Comments and notifications also have bounded cursor pagination. Do not precompute timelines until measurements justify the additional writes and revocation work.

Member discovery uses a persisted random key with an index. A per-browse random starting point wraps around that index, giving stable shuffled keyset pages without sorting the entire directory randomly per request. Search applies a literal, case-insensitive ordered-subsequence match to usernames and names. It allows missing letters, not arbitrary spelling corrections. Queries have a three-character minimum, 350 ms client debounce, and a server limit of 30 requests/member/minute. Filtered searches can still scan many profiles; monitor D1 rows read and introduce a dedicated search index if actual size/usage requires it. No hosted search service is added.

## Operating cost and recovery

Target $0 recurring provider charges within allowances; domain registration is separate. R2 may require billing setup even when usage is free. Free quotas are ceilings, not uptime guarantees. Monitor usage near 50%, 75%, and 90% of relevant allowances; enforce application upload limits before exhausting processing capacity. Budget alerts are not guaranteed hard caps.

Current planning allowances:

- Workers: free static requests; 100,000 dynamic requests/day, 10 ms CPU/invocation. Photos and auth routes consume dynamic requests too.
- D1: 5 million rows read and 100,000 rows written/day; 500 MB per free database, 5 GB account-wide. Index writes count toward usage. Free recovery window: seven days.
- R2 Standard: 10 GB-month, one million Class A and ten million Class B operations/month included; no egress fee. Storage continues to accrue while the app is idle.
- Images: 5,000 unique transformations/month on Free, then new transformations fail. Two variants roughly halve the upload allowance; avatars and retries must be accounted for. Persist variants to avoid repeated monthly transformations.

Instrument aggregate request/CPU/error metrics, database scans/writes, upload failures, object bytes, and transformations. Do not collect behavioral profiles. Keep persistent request logs disabled initially and redact user content from application errors. Baseline the actual beta workload rather than predicting capacity from user count alone.

The operations tooling now verifies encrypted exports and synthetic photo restoration; a disposable hosted database has passed a Time Travel drill. A nightly GitHub Actions job creates, restore-checks, and uploads an encrypted archive of D1 and all published photo variants to a separate provider (a private, write-only, versioned S3 bucket whose lifecycle deletes archives within about seven days), so a Cloudflare account or R2 failure cannot take the only copy. It costs well under a cent per month at current size and briefly pauses D1 queries during export at night. R2 durability is not backup protection against accidental deletion. See the operations runbook for retention, download, and manual backups. Recovery must preserve deletion records so restoring a backup does not resurrect access to deleted content. Document the recovery window and data-loss tolerance.

## Growth path

Production fetch handlers use a Washington-region placement hint to reduce round trips to the D1 primary observed in Seattle. Cloudflare chooses the nearby execution location; this is not an exact-city guarantee and does not provision Azure resources. Static assets retain edge delivery, and this setting does not relocate D1/R2 or scheduled handlers. See the dated measurements in the operations runbook before attributing improvements to placement.

1. Near free limits: upgrade Workers/D1 together as needed (Workers Paid starts at $5/month plus usage), and enable paid Images only when required. No application rewrite.
2. Excess scans or latency: fix indexes, queries, page sizes, and repeated reads before adding services. Add a durable queue for processing/cleanup only if synchronous latency or backlog warrants it.
3. Media delivery pressure: cache immutable bytes behind per-request authorization, use bounded authorization batching, and measure revocation correctness. Do not make private photos public for CDN convenience.
4. Database pressure: paid D1 caps each database at 10 GB and has single-database throughput constraints. Monitor size, contention, and latency well before those limits. Migrate the relational store to managed Postgres when needed; keep stable domain IDs, private R2 keys, and API contracts. This is an explicit migration with schema translation, validation, controlled write cutover, and rollback, not an automatic upgrade or cost-free ORM switch. Prefer a short controlled maintenance window to speculative dual writes.
5. Feed query pressure from large follow graphs: consider indexed timeline materialization or hybrid fan-out, preserving authoritative access checks. Implement only after load measurements identify the bottleneck.

## Optional device setup

Migration 0027 introduces account-level pending setup for future members only and allows multiple browser push endpoints to belong to one authenticated session. This models iOS cookie copying at installation without confusing session identity with isolated browser storage. Consent stays per endpoint; logout revokes every endpoint owned by that session. Migration preserves queued work and requires a maintenance window with the matching Worker. Bootstrap includes one additional indexed pending-state read, concurrent with the profile read. There is no new service, polling loop, device fingerprint, or client credential storage. See the device-setup and push feature READMEs for implemented behavior.

The October 15 client removes the optional installation/notification onboarding screen. Profile/photo completion opens the app directly, and Settings owns both opt-ins.

The same pending state now drives one device-setup row at the top of Activity on mobile devices. The row is client-rendered rather than an `activity_source` item: activity sources are actor-based social events with block/membership visibility and push enqueue triggers, and the unread count is account-wide while the right suggestion is device-specific. Bootstrap adds one indexed read for whether the member has any live push subscription, so an iPhone browser tab can skip Home Screen guidance it cannot otherwise verify. The client chooses the step from install state and local push permission/subscription without network requests; a per-device seen hint in browser storage limits the badge to one count per step. Answering No deletes the account's pending row. Migration 0028 is an automatic, insert-only backfill for members who predate 0027. No service, polling loop, device fingerprint, or new push behavior is added.

## Events

Events stay inside the existing Worker, D1 database, private R2 bucket, Better Auth magic links, and Activity/push pipeline; no service is added. A cover photo uses the trusted photo processor, quotas, and storage ledger.

Each event has one shareable URL, `/event/<token>`: an unguessable credential stored as a hash with recoverable ciphertext. Older fragment links remain valid with the same credential and invitation version. The server-visible URL lets crawlers read Open Graph metadata containing only the title and processed cover thumbnail; it adds no event directory or discovery API. The app serves no-referrer headers, and previews use noindex/nofollow and private/no-store responses. Application telemetry records route templates only, but the URL is necessarily visible to hosting infrastructure and the service receiving a shared link; external preview copies cannot be recalled. Hosts cannot replace it. It also invites new people to slowmass. Signed out, the current event link authorizes only a title/date/cover preview. The interactive signed-out preview metadata and processed thumbnail bytes use same-origin POST requests with the credential in the body, fresh link/publication/creator checks, and private/no-store responses; known members also respect creator blocks. Previewing creates no access row or membership. Covers reuse processed thumbnails without another transformation; a transient object URL is revoked when the client leaves or retries. Description, exact time, location, hosts, guests, and activity are excluded. Signing in through it binds a short-lived email claim to the exact link version; verification records an access row (event, member, link version) and, for new people, atomically creates a shared invitation from the event creator recording the event and link version, plus the membership. Opening the URL while signed in records the same access row. Access rows authorize viewing only while their version is current (only restore quarantine changes it); answering or hosting authorizes participation. Every request rechecks publication, the creator’s and viewer’s membership, and blocks in SQL, and full covers load only with a session. Cancelled or ended events retain the limited preview while admitting no new people. Invitation and access rows let an operator count joins per link version to trace mass sign-ups; cancelling the event stops further joins. Co-host invitations target existing members from a host’s accepted followers or following, using stable account IDs and requiring profile photos. Sending atomically records a pending invitation and current-link guest access, making the event visible in the recipient’s Events list. Acceptance rechecks the connection, memberships, blocks, inviting host, event state, and link version before granting a role. Email invitations are retired; membership provenance remains unchanged.

Creator-only event deletion reuses the existing deleted state. A guarded D1 batch records cover cleanup and clears media references and link ciphertext; current publication checks suppress all reads, admission, and queued push delivery. The event/link tombstone and invitation tree remain intact. No migration or new infrastructure is needed.

New members give only a name; the server generates a unique username. Members without a profile photo can use events, Activity, Settings, push, discovery, and other members’ identity/avatar previews. The people router gates relationship mutations and connection lists separately from discovery and profile reads; profile reads ignore legacy automatic follows until the viewer has a photo. Posting, following, and the feed still require a profile photo. No migration or new service is needed.

Event activity extends the Activity source table (migration 0030, a manual rebuild preserving receipts and queued push) rather than adding a parallel notification system. Keys identify the source, so no column is added. Fan-out is bounded by 500 answers per event; each host message writes one source per guest atomically with the message. Lists and the activity log read at most one page per index. Costs scale with D1 rows written per answer or message plus one photo per event; event pages add no polling. Sign-in email for new people uses the existing delivery budget and the [email upgrade path](#authorization-and-sessions) above.

Event appearance stores curated palette/font IDs on the event row. Migration 0034 adds the replacement font catalog alongside the original constrained column, preserving previous-Worker reads/writes without rebuilding the event table; the event feature documents legacy-choice resolution. A conditional host-authorized write protects against conflicting edits and changes no details or notifications. The same authorized event/preview reads return the IDs, so styling needs no extra API round trip. The client temporarily applies curated root variables while an event is mounted and restores them on exit. Openly licensed static font assets are public and content-addressed; event data and photos retain their private authorization/cache rules. The selected pairing is referenced on event pages and Create/Edit event; opening the Fonts dialog also references each preview’s faces. There is no remote font provider, preload catalog, or additional service.

## Google identity preparation

The local auth backend adds Google through the existing Better Auth/D1 boundary, with no new paid service. Provider identity attaches to the existing user ID after verified email matching; only consumer Gmail aliases collapse. A manual unique-index migration and collision audit protect concurrent creation without merging or rewriting stored accounts. Library-protected OAuth state pins the original invite/event claim; existing membership batches retain authority. Google tokens and profile photos are not retained. See the [auth contract](../src/server/auth/README.md) and [rollout prerequisites](setup.md#google-sign-in-preparation). The Google UI and production deployment remain pending.
