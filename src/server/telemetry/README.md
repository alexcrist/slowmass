# Request performance

API/media responses expose `Server-Timing` for handler wall time (`app`), summed D1 execution duration (`db`), and summed binding wait time (`dbwait`). Request-local counters collect statement count, rows read/written, and D1 duration through the binding boundary, including Better Auth. AsyncLocalStorage isolates concurrent requests; a memoized environment keeps auth-instance reuse intact. Prepared statements and atomic batches retain their normal behavior. `first()` reads the same result through `all()` to retain metadata; raw array reads and failed queries increment `unmeasuredQueries` because their row metadata is unavailable. Application request paths currently use measured `all`, `run`, `first`, and `batch` calls. Scheduled maintenance is outside this request scope.

`request.performance` JSON logs contain only route templates, method/status, request ID, timings/counts, and served media byte size. They never contain SQL, bind values, raw URLs, cookies, emails, user/post IDs, or content. Sampling defaults to 5% and can be changed with `PERFORMANCE_SAMPLE_RATE` (0–1); requests taking at least 500 ms and server errors are also emitted. Use `sampling="random"` at a consistent sample rate for latency percentiles; forced slow/error records intentionally overrepresent those cases. D1 rows describe measured statements, so inspect `unmeasuredQueries` before treating them as complete request totals. Media bytes mean selected object size, not proof that the client downloaded the whole body.

Logs are available through local Wrangler output or a live tail; normal requests provision no logging service or durable telemetry records. Abnormal startup requests retain bounded snapshots in the existing D1 database; see [startup diagnostics](../diagnostics/README.md). Persistent provider log collection is not enabled. Provider-generated invocation envelopes can contain raw request metadata, so retain/export only the sanitized application records when collecting measurements. Aggregate hosted CPU and account usage remain available through `scripts/ops/usage.mjs`. Handler wall time is not CPU time and excludes response-body transfer and client rendering; no per-route CPU measurement is claimed.

An API/media handler still running after five seconds emits one unsampled `request.stalled` record with its safe request ID, route template, and current counters. `pendingQueries` counts unfinished statements, including batch members. `databaseWaitMs` measures completed binding calls including queue/transport wait; `databaseMs` comes from D1 execution metadata. Parallel call waits can overlap, so their sum can exceed handler wall time. An unfinished call is represented by `pendingQueries`, not yet added to completed wait time. Neither measure includes image processing or response-body transfer.

For a stalled bootstrap, zero database calls plus an `auth.timeout` in initialization points toward auth startup. A positive pending count points toward the D1 call boundary, but does not alone distinguish provider queuing from transport. Completed calls with large binding waits and short execution time suggest delay outside SQL execution. These are diagnostic clues, not automatic root-cause classifications. Abnormal startup snapshots retain these counters and coarse phases for later inspection. General durable provider log collection is still disabled.

Private avatar and post-image reads also record `storageReads` and `storageWaitMs`, exposed as `r2` in `Server-Timing`. These measure the R2 get call through receipt of the object response, including missing objects and failures. They preserve the response stream and exclude body transfer, browser decoding, and rendering. No object keys or content are logged. Compare these timings before attributing non-database latency to storage or changing image quality/caching.
