# Private avatars

An active member with a saved profile can upload an avatar to complete onboarding, even before other member APIs are available. A profile photo is required: the removal endpoint rejects requests, and updates replace the existing photo. Account deletion still removes avatar data. Uploads reserve an actor-scoped idempotency key and bounded processing attempt before reading bytes. Successful retries acknowledge the original operation without another transformation; failed/in-progress keys cannot be reused to bypass quotas. Choose the file again to start a new attempt after a confirmed processing failure.

The trusted photo processor creates a 320px WebP avatar and a large WebP up to 1600px, using the same quality and metadata stripping as posts. Small inputs share one object without upscaling. Originals are never stored. R2 writes have durable cleanup intent before upload; a database batch switches the current avatar, queues both previous objects for deletion, and marks the attempt complete. The scheduled handler deletes up to two due unreferenced objects and retries failed deletions later. New orphan objects receive a one-hour grace period.

Every media request checks active membership and both block directions. Avatars are visible to signed-in, unblocked members before a follow is accepted. The default URL serves the small avatar; `?size=large` serves the large version. Existing photos fall back to their small object with no backfill. URLs identify a handle rather than an object key; replacement/account deletion immediately prevents access to the prior object. Responses are private and no-store. There are no public R2 URLs.

Initial limits: five attempts per member per rolling day, 150 across the app per rolling day, and 3,500 reserved transformation units per UTC calendar month, shared with posts and legacy-thumbnail conversion. New avatars and posts each reserve two units, including when a small input shares one object. Failed attempts count. These leave room below the Images free allowance; other services or direct account use still count toward provider limits. Attempt records expire after 60 days, bounding idempotency retention. Body, format, pixel, and output limits live in the photo processor.
