# Events

Members with a profile photo create events with one cover photo, a title, description, plain-text location (no maps or geotagging), a start time, an optional end time within 30 days, and the creator's IANA time zone. Hosts and guests answer Going, Maybe, or Can’t go. An event without an end time is over twelve hours after it starts; answers then close. Hosts can edit details, replace the cover photo, add or remove hosts, and cancel. An event’s link never changes. Cancelled events stay readable with answers closed. Only the creator can delete an event, including cancelled or past events; deletion removes it for everyone without sending notifications.

Creation is a draft until its cover photo is processed. The draft, its host row, and a ten-per-day creation allowance commit in one batch; retrying the same ID, details, and appearance converges, while different details or appearance conflict. Cover uploads use an `Idempotency-Key`, the shared photo-processing allowance (two units for full size and a 480px thumbnail), and storage reservation, following the avatar replacement pattern: old keys enter cleanup and new keys leave it only when the event references them. Scheduled cleanup deletes unreferenced `events/` objects in small batches, marks drafts without a photo deleted after a day, removes expired email claims, and removes unusable member co-host invitations and retired email invitations (100 of each per pass).

## Access

Each event has one shareable URL, `/event/<token>`, and texting it invites people to the event and, if they are new, to slowmass. The token is 48 random characters whose SHA-256 hash is indexed and whose ciphertext (Better Auth encryption with `AUTH_SECRET`) lets anyone who can see the event get the URL again; the event view returns it so the page can share it and show it in the address bar. Older `/#event/<token>` links continue to open with the same token and invitation version; only newly copied URLs support crawler previews. Signed out, `POST /api/event-link` returns only the event ID, whether it admits new people, and a preview containing title, formatted date in the event’s time zone, and cover dimensions. Description, exact time, location, and member information are never selected for this response. `POST /api/event-link/photo` returns the existing processed thumbnail after independently checking the current credential, publication, and active creator; known signed-in viewers also respect creator blocks on both endpoints. These interactive requests keep the credential in the body, every response is private/no-store, and internal byte-cache reuse follows fresh authorization. Invalid, old, unpublished, or deleted links expose neither preview nor image. Cancelled/ended events retain the preview but admit no new people. Preview reads create no access or membership rows; signing in through it is handled by [membership](../../membership/README.md). Signed in, `POST /api/events/open` records an access row with the current link version and returns the event. Opening grants viewing—details, cover, and hosts—while that version is current. Answering (or hosting) adds the guest list, answer counts, activity, and messages, and survives a version change. Hosts cannot replace a link; only restore quarantine gives an event a new, unusable version, which stops the old URL, pending sign-ins, and access from merely opening it. Without ciphertext the view returns no URL, so a quarantined event invites no one new. To stop a leaked link from admitting people, cancel the event.

Every read and write rechecks, in SQL, that the event is published, its creator is active, the viewer is active, and neither has blocked the other. A block with any other guest or co-host hides that person from lists and the log. Inactive members disappear from lists. Full covers load only with a session after the same checks; the limited preview uses the link-authorized thumbnail described above. Hosts appear with their name and their normal private avatar.

## Link previews and unlisted discovery

`GET /event/:token` serves the normal app shell with server-rendered Open Graph and Twitter card metadata. Its indexed query selects only the title, and `/event/:token/photo` returns the existing processed thumbnail after fresh authorization. Neither endpoint selects or embeds a description, date, time, location, host, guest, email, RSVP, or invitation provenance. HTML text and attributes are escaped. No extra transformation, public bucket, migration, or service is needed. Worker-first asset routing is required so crawlers get this HTML instead of the generic SPA shell.

HTML and image requests recheck the current credential, publication, active creator, and blocks for known viewers before reading any cached bytes. They create no access, membership, or answer rows. Invalid/revoked/deleted/unpublished links fail closed; cancellation or the end time retains the limited preview without admitting new members. Responses use private/no-store, noindex/nofollow, and no-referrer; HTML also prevents response transformation. Application telemetry records route templates, never the token. The token now reaches hosting infrastructure and link-preview providers, and already downloaded previews cannot be recalled. These public fields are available to anyone who obtains the URL, including when signed out.

There is no event discovery endpoint. Account lists include only events the member created, opened through their current link, answered, or accepted hosting for; accepting hosting itself requires prior event access. Accepted follows alone grant neither discovery nor viewing. Sending a member co-host invitation explicitly shares the current event link’s guest access, so the event appears in the recipient’s Events list. Old pending email invitations grant no access. Direct event-ID reads, covers, calendar exports, guest lists, and activity remain subject to the existing access checks. Workers/D1 tests cover followers, pending hosts, strangers, members without profile photos, anonymous crawlers, safe HTML encoding, no preview side effects, retained account access, and denial after deletion or credential changes. Actual third-party unfurl appearance and provider caching remain unverified.

## Deletion

Creator deletion uses the existing deleted state, with no migration. The active creator is checked in every statement of one transaction that queues both cover objects for cleanup, clears media references and link ciphertext, and redacts the title, description, and location. Retries, including concurrent retries or a lost success response, converge. Failure rolls back both deletion and cleanup intent. A cover upload already in progress cannot republish the deleted event; its unreferenced objects retain cleanup intent.

All existing publication predicates immediately exclude the event from upcoming/past lists, details, calendar export, guests, activity, media (including warm internal cache entries), previews, and new or pending link sign-ins. Activity/badge reads and queued push eligibility also exclude it. Deletion sends no cancellation or other alert. There is no restore action. Already delivered notifications and external calendar copies cannot be recalled.

The event/creator/link identities, original issuance time, invitation records, and memberships survive so joins remain traceable and admitted members keep their accounts. Existing host, answer, message, and access rows remain stored but inaccessible; pending host emails and expired claims drain through existing bounded cleanup. Cover objects and storage accounting drain through the normal retryable cleanup queue. Integration tests cover authorization, retries, rollback, cached bytes, retained provenance, pending admission, queued push suppression, and an upload finishing after deletion.

## Calendar download

The calendar-file read uses the same current event-viewing predicate as event details, with an additional cancellation check. Hosts, people who answered, and people who opened the current link may download it, including members without a profile photo; anonymous/expired sessions, strangers, creator blocks, inactive membership, obsolete link access, unpublished/deleted events, and cancelled events are denied. Every download rechecks access with one indexed event query. It writes nothing and uses private/no-store plus text/calendar and an attachment filename; there is no public calendar feed, subscription credential, storage object, or new service.

The file contains event details and an ID-based return link that requires existing access, never the invite credential, guest list, host emails, or cover bytes. A stable event UID identifies repeat exports. The [shared formatter](../../../shared/event-calendar/README.md) escapes text and preserves UTC instants. Downloaded copies are outside slowmass and are not synchronized by later edits, cancellation, or access changes. Workers/D1 tests verify session and access denial after successful downloads, file headers, unchanged RSVP state, and invitation exclusion.

## Hosts

The creator hosts and can never be removed. Hosts search their accepted followers and following, in explicit pages of twenty, and invite existing active members with profile photos. Search matches literal substrings of names and usernames, case-insensitively; it never searches emails. Pending follows, blocked members, incomplete profiles, existing hosts, and pending invitees are excluded. Both searching and sending recheck host authority, current relationships, and the event’s open state. An event holds at most ten accepted and pending hosts; conditional inserts enforce the cap under concurrent requests.

Invitations use stable account IDs, recording the inviting host and current event-link version. Sending commits the invitation and ordinary guest access together, so the event appears in the recipient’s Events list with “Asked to co-host.” Acceptance is still required before host privileges or host notifications begin. Acceptance rechecks the recipient’s profile photo, current accepted connection, both memberships, blocks, inviter’s host role, event state, and link version. Retries converge. Hosts can remove pending invitations or other co-hosts; co-hosts can leave, but the creator stays. Declining or removing hosting retains guest access already shared. These actions never create memberships or change invitation-tree provenance.

Email co-host invitations are retired: email bodies are rejected, pending email rows are never read for authorization or returned to hosts, and bounded cleanup drains their addresses. Migration 0035 adds the member invitation table without changing the previous Worker’s schema or data. The event response retains an empty legacy `pendingHosts` array for already-loaded clients; current clients use `pendingHostMembers`. Existing co-hosts retain their roles. Cleanup removes stale member invitations after closure, deletion, link-version changes, sender removal, account disablement/deletion, lost connections, or blocks; restored backups clear both invitation tables. No email or push is sent for a co-host invitation; recipients find it in Events.

## Answers, guests, and activity

Who may answer lives in [membership](../../membership/README.md) alongside link sign-in: hosts answer like guests without needing the link, a guest’s first answer needs an opened current link, at most 500 people answer an event (bounding notification fan-out), and an unchanged answer keeps its timestamp. Guest lists page 30 people per answer, newest change first. The event’s activity log merges each current answer with messages, newest first, reading at most one page from each index before merging 20 items. Hosts and guests post plain-text messages up to 2,000 characters (100 a day per member), retry-safe by client UUID. Authors and hosts can remove ordinary messages. All detail edits are silent, including time and location; historical `changed` entries are excluded from the event log and Activity. Cancelling still records `cancelled`. A conditional update guards edits against concurrent changes to any detail and rechecks host access in the write.

Answers and messages feed [Activity](../notifications/README.md): hosts hear about each other person’s current answer, including other hosts’, every message reaches the other hosts, and host messages and cancellation also reach everyone who answered. Push and email follow each member’s [notification preferences](../notifications/README.md); by default only update blasts are emailed. Successful answer, message, update blast, and cancellation requests start best-effort push dispatch; the durable outbox and hourly fallback recover missed work. Dispatch remains bounded and rechecks current access and unread state; see [push](../push/README.md).

Hosts send an update blast: a plain-text message that reaches every other host and everyone who answered (including Maybe and Can’t go) in Activity. Merely opening a link does not subscribe someone. A blast is an ordinary host message with `blast=1` (migration 0037), so the event log, Activity sources, read state, and the push and email queues commit together through the existing and notification triggers. Recipients get it by push and email according to their [notification preferences](../notifications/README.md), with email on by default, and the sending host gets a copy by email. The host-only mutation rechecks active membership, creator blocks, publication, and hosting in both the write and the retry acknowledgement; cancelled events reject it. Unchanged retries preserve the message ID and create no duplicate alerts or emails, while different text conflicts. An ordinary message ID cannot become a blast, or the reverse. Blasts share the message length and 100-a-day allowance, and each event sends at most three a day across all its hosts, which bounds blast email per event to about 1,500 a day. Normal message deletion removes their Activity and stops unsent alerts. A successful request confirms persistence, not delivery: email and push leave through the notification outboxes, rechecked at send time, at most 20 emails and 10 pushes per pass, after the request and every minute.

Members without a profile photo can use events, Activity, Settings, push, discovery, and other members’ identity/avatar previews; following, posting, and the feed still require a profile photo. Account deletion ends a creator’s events (photos to cleanup, ciphertext cleared) and removes the person’s hosting rows, access rows, answers, messages, and pending claims.

Integration tests in `tests/events.test.ts` and `tests/worker.test.ts` cover creation limits and retries, signed-out link checks, opening and recorded link versions, viewing versus participating, media for members, strangers, and anonymous requests, blocked, inactive, and new-link-version cases, answer rules including hosts, connected-member co-host invitations, acceptance, removal, limits and cleanup, closing times, pagination, messages, notifications, joining through a link with a name-only profile, account deletion, photo processing, migration 0030 preservation, and update blast recipients, the host's copy, preferences, retries, abandoned claims, and limits.

Cover failure handling preserves a completed attempt if the save batch commits but its response is lost; only pending attempts become failed. Shared photo ingestion/processing deadlines apply before storage. An unchanged retry can acknowledge a completed cover without another transformation.

## Appearance

Migration 0033 adds defaulted, constrained color-theme and font-pairing IDs. Existing events and creation requests that omit appearance keep Original. Creation accepts the curated pair and writes it atomically with the draft, before the cover publishes it; matching retries converge and conflicting appearance returns a conflict. Ordinary detail updates never touch appearance. The shared validator accepts curated IDs only, never CSS or URLs. Current active, unblocked hosts of a published, uncancelled event can update appearance independently of details. A single conditional SQL write rechecks authorization and compares the host’s previously read pair; conflicting co-host saves fail, while an identical retry succeeds. No notification, log entry, image processing, or polling is added.

Authorized event reads include the saved pair. A current event link also reveals these IDs in its signed-out preview, alongside the existing title/date/cover fields; it reveals no additional member or detail data. Preview authorization and private/no-store responses are unchanged. A failed or timed-out save may already have committed: retry the same choices, or reload to read the saved pair. New choices after another host’s edit require a fresh read.

Migration 0034 adds a nullable, constrained second font column instead of rebuilding the event table or modifying its applied constraint. Existing Poster, Rounded, and Geometric choices resolve to Bungee Shade, Fascinate Inline, and Monoton respectively; Original, Handwritten, and Classic remain unchanged. Current writes use the second column. Reads, retry checks, and concurrency guards share this effective choice, so an existing event can be edited immediately. The original column stays readable/writable by the previous Worker if deployment fails or is rolled back. A previous-Worker font write clears the new choice so that edit takes precedence; detail edits preserve it. No backfill or dependent-row changes are required.

Signed-in link admission returns the ID plus the same authorized detail view as a direct event read, saving a second HTTP/authentication round trip. Detail selection rechecks current access after recording the link version; failure returns the usual unavailable-link response. Retries retain the existing idempotent admission behavior. The ID stays in the response for already-loaded clients; signed-out previews are unchanged.
