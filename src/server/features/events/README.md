# Events

Members with a profile photo create events with one cover photo, a title, description, plain-text location (no maps or geotagging), a start time, an optional end time within 30 days, and the creator's IANA time zone. Hosts and guests answer Going, Maybe, or Can’t go. An event without an end time is over twelve hours after it starts; answers then close. Hosts can edit details, replace the cover photo, add or remove hosts, and cancel. An event’s link never changes. Cancelled events stay readable with answers closed; there is no deletion apart from account deletion.

Creation is a draft until its cover photo is processed. The draft, its host row, and a ten-per-day creation allowance commit in one batch; retrying the same ID and details converges, while different details conflict. Cover uploads use an `Idempotency-Key`, the shared photo-processing allowance (two units for full size and a 480px thumbnail), and storage reservation, following the avatar replacement pattern: old keys enter cleanup and new keys leave it only when the event references them. Scheduled cleanup deletes unreferenced `events/` objects in small batches, marks drafts without a photo deleted after a day, removes expired email claims, and removes pending host emails (100 per pass) once their event is over, cancelled, or gone.

## Access

Each event has one URL, `/#event/<token>`, and texting it invites people to the event and, if they are new, to slowmass. The token is 48 random characters whose SHA-256 hash is indexed and whose ciphertext (Better Auth encryption with `AUTH_SECRET`) lets anyone who can see the event get the URL again; the event view returns it so the page can share it and show it in the address bar. The token stays in URL fragments and request bodies, never in a server-visible URL. Signed out, `POST /api/event-link` returns only the event ID, whether it admits new people, and a preview containing title, formatted date in the event’s time zone, and cover dimensions. Description, exact time, location, and member information are never selected for this response. `POST /api/event-link/photo` returns the existing processed thumbnail after independently checking the current credential, publication, and active creator; known signed-in viewers also respect creator blocks on both endpoints. The credential stays in the request body, every response is private/no-store, and internal byte-cache reuse follows fresh authorization. Invalid, old, unpublished, or deleted links expose neither preview nor image. Cancelled/ended events retain the preview but admit no new people. Preview reads create no access or membership rows; signing in through it is handled by [membership](../../membership/README.md). Signed in, `POST /api/events/open` records an access row with the current link version and returns the event. Opening grants viewing—details, cover, and hosts—while that version is current. Answering (or hosting) adds the guest list, answer counts, activity, and messages, and survives a version change. Hosts cannot replace a link; only restore quarantine gives an event a new, unusable version, which stops the old URL, pending sign-ins, and access from merely opening it. Without ciphertext the view returns no URL, so a quarantined event invites no one new. To stop a leaked link from admitting people, cancel the event.

Every read and write rechecks, in SQL, that the event is published, its creator is active, the viewer is active, and neither has blocked the other. A block with any other guest or co-host hides that person from lists and the log. Inactive members disappear from lists. Full covers load only with a session after the same checks; the limited preview uses the link-authorized thumbnail described above. Hosts appear with their name and their normal private avatar.

## Hosts

The creator hosts and can never be removed. Any host adds another by email (`POST /api/events/:id/hosts`), and the reply is identical whether or not an account uses the address, so adding reveals nothing. Emails travel only in request bodies and are visible only to the event’s hosts. An event holds at most ten hosts including pending emails, and hosts are added only while it is open. A member signed in with a pending email, with a profile photo and access to the event (an opened current link, or an answer), sees `viewer.hostInvited`; accepting (`POST /api/events/:id/hosting`) is their consent to appear as a host to everyone with the link, and declining (`DELETE`) removes the email. Accepting is retry-safe and removes the pending email in the same batch. Any host removes pending emails or co-hosts, and co-hosts can stop hosting; both converge on retry. Removed hosts keep any access they had as guests. New hosts hear about answers and messages from then on; earlier activity is not backfilled. Account deletion removes pending emails addressed to that account.

## Answers, guests, and activity

Who may answer lives in [membership](../../membership/README.md) alongside link sign-in: hosts answer like guests without needing the link, a guest’s first answer needs an opened current link, at most 500 people answer an event (bounding notification fan-out), and an unchanged answer keeps its timestamp. Guest lists page 30 people per answer, newest change first. The event’s activity log merges each current answer with messages, newest first, reading at most one page from each index before merging 20 items. Hosts and guests post plain-text messages up to 2,000 characters (100 a day per member), retry-safe by client UUID. Authors and hosts can remove ordinary messages. Changing the time or location records a `changed` entry listing what changed; cancelling records `cancelled`. Title and description edits are silent. A conditional update guards edits against concurrent changes to time, zone, or location.

Answers and messages feed [Activity](../notifications/README.md): hosts hear about each other person’s current answer, including other hosts’, every message reaches the other hosts, and host messages, changes, and cancellation also reach everyone who answered. No email is sent for event activity; Web Push follows the member’s existing opt-in. Successful answer, message, detail-edit, and cancellation requests start best-effort push dispatch; the durable outbox and hourly fallback recover missed work. Dispatch remains bounded and rechecks current access and unread state; see [push](../push/README.md).

Members without a profile photo can use events, Activity, and push; everything else still requires a profile photo. Account deletion ends a creator’s events (photos to cleanup, ciphertext cleared) and removes the person’s hosting rows, access rows, answers, messages, and pending claims.

Integration tests in `tests/events.test.ts` and `tests/worker.test.ts` cover creation limits and retries, signed-out link checks, opening and recorded link versions, viewing versus participating, media for members, strangers, and anonymous requests, blocked, inactive, and new-link-version cases, answer rules including hosts, co-host invitations, acceptance, removal, limits and cleanup, closing times, pagination, messages, notifications, joining through a link with a name-only profile, account deletion, photo processing, and migration 0030 preservation.

Cover failure handling preserves a completed attempt if the save batch commits but its response is lost; only pending attempts become failed. Shared photo ingestion/processing deadlines apply before storage. An unchanged retry can acknowledge a completed cover without another transformation.
