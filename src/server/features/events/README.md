# Events

Members with a profile photo create events with one cover photo, a title, description, plain-text location (no maps or geotagging), a start time, an optional end time within 30 days, and the creator's IANA time zone. Hosts and guests answer Going, Maybe, or Can’t go. An event without an end time is over twelve hours after it starts; answers then close. Hosts can edit details, replace the cover photo, add or remove hosts, and cancel. An event’s link never changes. Cancelled events stay readable with answers closed. Only the creator can delete an event, including cancelled or past events; deletion removes it for everyone without sending notifications.

Creation is a draft until its cover photo is processed. The draft, its host row, and a ten-per-day creation allowance commit in one batch; retrying the same ID and details converges, while different details conflict. Cover uploads use an `Idempotency-Key`, the shared photo-processing allowance (two units for full size and a 480px thumbnail), and storage reservation, following the avatar replacement pattern: old keys enter cleanup and new keys leave it only when the event references them. Scheduled cleanup deletes unreferenced `events/` objects in small batches, marks drafts without a photo deleted after a day, removes expired email claims, and removes pending host emails (100 per pass) once their event is over, cancelled, or gone.

## Access

Each event has one URL, `/#event/<token>`, and texting it invites people to the event and, if they are new, to slowmass. The token is 48 random characters whose SHA-256 hash is indexed and whose ciphertext (Better Auth encryption with `AUTH_SECRET`) lets anyone who can see the event get the URL again; the event view returns it so the page can share it and show it in the address bar. The token stays in URL fragments and request bodies, never in a server-visible URL. Signed out, `POST /api/event-link` returns only the event ID, whether it admits new people, and a preview containing title, formatted date in the event’s time zone, and cover dimensions. Description, exact time, location, and member information are never selected for this response. `POST /api/event-link/photo` returns the existing processed thumbnail after independently checking the current credential, publication, and active creator; known signed-in viewers also respect creator blocks on both endpoints. The credential stays in the request body, every response is private/no-store, and internal byte-cache reuse follows fresh authorization. Invalid, old, unpublished, or deleted links expose neither preview nor image. Cancelled/ended events retain the preview but admit no new people. Preview reads create no access or membership rows; signing in through it is handled by [membership](../../membership/README.md). Signed in, `POST /api/events/open` records an access row with the current link version and returns the event. Opening grants viewing—details, cover, and hosts—while that version is current. Answering (or hosting) adds the guest list, answer counts, activity, and messages, and survives a version change. Hosts cannot replace a link; only restore quarantine gives an event a new, unusable version, which stops the old URL, pending sign-ins, and access from merely opening it. Without ciphertext the view returns no URL, so a quarantined event invites no one new. To stop a leaked link from admitting people, cancel the event.

Every read and write rechecks, in SQL, that the event is published, its creator is active, the viewer is active, and neither has blocked the other. A block with any other guest or co-host hides that person from lists and the log. Inactive members disappear from lists. Full covers load only with a session after the same checks; the limited preview uses the link-authorized thumbnail described above. Hosts appear with their name and their normal private avatar.

## Deletion

Creator deletion uses the existing deleted state, with no migration. The active creator is checked in every statement of one transaction that queues both cover objects for cleanup, clears media references and link ciphertext, and redacts the title, description, and location. Retries, including concurrent retries or a lost success response, converge. Failure rolls back both deletion and cleanup intent. A cover upload already in progress cannot republish the deleted event; its unreferenced objects retain cleanup intent.

All existing publication predicates immediately exclude the event from upcoming/past lists, details, calendar export, guests, activity, media (including warm internal cache entries), previews, and new or pending link sign-ins. Activity/badge reads and queued push eligibility also exclude it. Deletion sends no cancellation or other alert. There is no restore action. Already delivered notifications and external calendar copies cannot be recalled.

The event/creator/link identities, original issuance time, invitation records, and memberships survive so joins remain traceable and admitted members keep their accounts. Existing host, answer, message, and access rows remain stored but inaccessible; pending host emails and expired claims drain through existing bounded cleanup. Cover objects and storage accounting drain through the normal retryable cleanup queue. Integration tests cover authorization, retries, rollback, cached bytes, retained provenance, pending admission, queued push suppression, and an upload finishing after deletion.

## Calendar download

The calendar-file read uses the same current event-viewing predicate as event details, with an additional cancellation check. Hosts, people who answered, and people who opened the current link may download it, including members without a profile photo; anonymous/expired sessions, strangers, creator blocks, inactive membership, obsolete link access, unpublished/deleted events, and cancelled events are denied. Every download rechecks access with one indexed event query. It writes nothing and uses private/no-store plus text/calendar and an attachment filename; there is no public calendar feed, subscription credential, storage object, or new service.

The file contains event details and an ID-based return link that requires existing access, never the invite credential, guest list, host emails, or cover bytes. A stable event UID identifies repeat exports. The [shared formatter](../../../shared/event-calendar/README.md) escapes text and preserves UTC instants. Downloaded copies are outside slowmass and are not synchronized by later edits, cancellation, or access changes. Workers/D1 tests verify session and access denial after successful downloads, file headers, unchanged RSVP state, and invitation exclusion.

## Hosts

The creator hosts and can never be removed. Any host adds another by email (`POST /api/events/:id/hosts`), and the reply is identical whether or not an account uses the address, so adding reveals nothing. Emails travel only in request bodies and are visible only to the event’s hosts. An event holds at most ten hosts including pending emails, and hosts are added only while it is open. A member signed in with a pending email, with a profile photo and access to the event (an opened current link, or an answer), sees `viewer.hostInvited`; accepting (`POST /api/events/:id/hosting`) is their consent to appear as a host to everyone with the link, and declining (`DELETE`) removes the email. Accepting is retry-safe and removes the pending email in the same batch. Any host removes pending emails or co-hosts, and co-hosts can stop hosting; both converge on retry. Removed hosts keep any access they had as guests. New hosts hear about answers and messages from then on; earlier activity is not backfilled. Account deletion removes pending emails addressed to that account.

## Answers, guests, and activity

Who may answer lives in [membership](../../membership/README.md) alongside link sign-in: hosts answer like guests without needing the link, a guest’s first answer needs an opened current link, at most 500 people answer an event (bounding notification fan-out), and an unchanged answer keeps its timestamp. Guest lists page 30 people per answer, newest change first. The event’s activity log merges each current answer with messages, newest first, reading at most one page from each index before merging 20 items. Hosts and guests post plain-text messages up to 2,000 characters (100 a day per member), retry-safe by client UUID. Authors and hosts can remove ordinary messages. All detail edits are silent, including time and location; historical `changed` entries are excluded from the event log and Activity. Cancelling still records `cancelled`. A conditional update guards edits against concurrent changes to any detail and rechecks host access in the write.

Answers and messages feed [Activity](../notifications/README.md): hosts hear about each other person’s current answer, including other hosts’, every message reaches the other hosts, and host messages and cancellation also reach everyone who answered. No email is sent for event activity; Web Push follows the member’s existing opt-in. Successful answer, message, host-notification, and cancellation requests start best-effort push dispatch; the durable outbox and hourly fallback recover missed work. Dispatch remains bounded and rechecks current access and unread state; see [push](../push/README.md).

Hosts can explicitly send a notification with a plain-text message. This writes an ordinary host message, so the event log, Activity sources, read state, and opt-in push queue commit together using the existing triggers. Every other host and everyone who answered receives Activity regardless of push opt-in, including Maybe and Can’t go; merely opening a link does not subscribe someone. There is no email. The host-only mutation rechecks active membership, creator blocks, publication, and hosting in both the write and retry acknowledgement; cancelled events reject it. Unchanged retries preserve the message ID and create no duplicate alerts, while different text conflicts. Notifications share the message length and daily allowance, and normal message deletion removes their Activity. Push delivery retains the bounded queue and timing limits documented in [push](../push/README.md); a successful send confirms persistence, not delivery to every device. No migration is required.

Members without a profile photo can use events, Activity, and push; everything else still requires a profile photo. Account deletion ends a creator’s events (photos to cleanup, ciphertext cleared) and removes the person’s hosting rows, access rows, answers, messages, and pending claims.

Integration tests in `tests/events.test.ts` and `tests/worker.test.ts` cover creation limits and retries, signed-out link checks, opening and recorded link versions, viewing versus participating, media for members, strangers, and anonymous requests, blocked, inactive, and new-link-version cases, answer rules including hosts, co-host invitations, acceptance, removal, limits and cleanup, closing times, pagination, messages, notifications, joining through a link with a name-only profile, account deletion, photo processing, and migration 0030 preservation.

Cover failure handling preserves a completed attempt if the save batch commits but its response is lost; only pending attempts become failed. Shared photo ingestion/processing deadlines apply before storage. An unchanged retry can acknowledge a completed cover without another transformation.

## Appearance

Migration 0033 adds defaulted, constrained color-theme and font-pairing IDs. Existing events and old-client inserts keep Original; ordinary detail updates never touch appearance. The shared validator accepts curated IDs only, never CSS or URLs. Current active, unblocked hosts of a published, uncancelled event can update appearance independently of details. A single conditional SQL write rechecks authorization and compares the host’s previously read pair; conflicting co-host saves fail, while an identical retry succeeds. No notification, log entry, image processing, or polling is added.

Authorized event reads include the saved pair. A current event link also reveals these IDs in its signed-out preview, alongside the existing title/date/cover fields; it reveals no additional member or detail data. Preview authorization and private/no-store responses are unchanged. A failed or timed-out save may already have committed: retry the same choices, or reload to read the saved pair. New choices after another host’s edit require a fresh read.
