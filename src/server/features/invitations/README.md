# Member invitations

An active verified member with a profile photo can invite a specific email. The session determines the inviter; membership owns issuance eligibility and atomic acceptance. There is no daily invitation limit per member; shared email-delivery budgets still apply. The feature creates eligibility, then sends an invitation through the shared Resend transport. Repeating the same outstanding invitation reuses its record, and confirmed sends do not send again. The member can explicitly send or retry their own unaccepted, unrevoked, unexpired invitation from history; older invitations are not automatically emailed.

The email uses the inviter’s profile name and username, identifies slowmass as a Seattle-based social media application for sharing photos with friends, and contains a personal Join slowmass link. Opening it previews the invitation; explicitly accepting verifies the invited email and signs the recipient in through Better Auth. The link expires with the invitation after seven days and never authenticates an existing member. The recipient does not need a second email. Old emails without join links still support the normal email sign-in path.

Creation time and attribution remain immutable, including after expiry/cancellation. First email-attempt time, last attempt, and first confirmed provider acceptance are recorded separately in Unix milliseconds. Provider acceptance is not proof of inbox delivery. History exposes these timestamps only to the inviter, never the frozen transport payload.

An atomic one-minute send claim bounds concurrent retries. The first request payload is frozen across retries, including inviter identity, recipient, subject, sender, body, and credential. Better Auth's authenticated encryption protects this retry payload with `AUTH_SECRET`; the invitation otherwise stores only a SHA-256 token hash. A versioned invitation-scoped [Resend idempotency key](https://resend.com/docs/dashboard/emails/idempotency-keys) prevents duplicate delivery within its documented 24-hour window. Unconfirmed retries stop after 23 hours to leave a safety margin; the member can cancel and create a new invitation. A timeout is reported as unconfirmed, not success. Shared daily/recipient budgets include invitation emails and failed attempts. No background email delivery queue or service is introduced.

The payload is cleared after confirmed provider acceptance or cancellation. Scheduled cleanup clears up to 50 old, accepted, revoked, or inactive-inviter payloads per pass using a partial index; recipient account deletion also clears payloads during redaction. Provenance and delivery timestamps remain. Cancellation can race with an in-flight provider request, but any resulting email cannot bypass revoked eligibility. A missing encrypted retry payload cannot mint a replacement credential under the same provider key. After secret rotation, an undecryptable pending send must be cancelled and reissued; successfully sent links do not depend on that secret.

Personal history uses inviter-scoped 20-row keyset pages and an index limited to personal invitations, keeping shared redemptions out of page scans. Cancellation is idempotent and only affects unaccepted invitations. Membership rechecks revocation when an email link is consumed. Failure responses allow retry without revealing another inviter’s history.

The feature domain owns issuance/reuse, history pagination, cancellation, and retry-payload retention. HTTP handlers only authenticate, validate request input, call these functions, and map their outcomes. The application scheduler calls the feature’s cleanup entry point; it contains no invitation SQL.

## Current invite link

Migration 0025 implements one rotating credential per completed active inviter with seven-day expiry and no sign-up cap. Copy reuses a valid credential without extending expiry; absent/expired credentials are created through a conditional upsert. The owner key enforces one row, and concurrent copies return the winning credential. Owner metadata omits the credential. Replacement compares the selected version, installs a fresh credential in one write, and replays the same operation ID without replacing again. A stale operation cannot overwrite a newer version. Source records for successful joins retain immutable invitation type and member provenance independently of this rotating row. Shared-link history and per-link joiner APIs are removed.

The bearer credential is returned through authenticated, same-origin copy/replacement responses and carried in `/invite#…`. A hash supports lookup; Better Auth authenticated encryption with `AUTH_SECRET` protects the recoverable copy. Copy after secret rotation can fail; the owner can replace the link through Link options. Expired, revoked, and inactive-inviter encrypted credentials are cleared in bounded scheduled batches. Account cleanup preserves the inviter tombstone and permanent joins while clearing ciphertext.

A credential holder can preview the inviter’s name/handle and expiry, with no avatar, recipient list, private bio, or posts. The existing auth-library preview/request throttles and shared application/recipient email budgets remain authoritative. Membership owns email-bound claims and atomic redemption, including exact credential-version checks; this feature owns current-link management and cleanup. Forwarding a link permits anyone receiving it to request admission during its lifetime. Replacement revokes the previous credential and outstanding verification attempts; it does not affect joined accounts.

Migration 0025 is deployed. It discards unused old links and requires no shared redemptions or claims; it aborts if either exists. The deployment must use maintenance and matching code/schema, as described in the operations runbook. No legacy shared-link endpoints or compatibility flow remain.
