# In-app notifications

Activity combines incoming follow requests, new followers, grouped likes on owned published posts, and undeleted comments. Self-interactions produce no notification. Current membership and blocks in either direction are checked on every read. Deleted posts, removed likes, deleted comments, and resolved requests disappear; acceptance replaces its request with a new unread follower event. Opening a target reauthorizes through its profile or post API.

Migration 0017 adds an indexed directory of interaction sources. SQLite triggers maintain it atomically with inserts, updates, and deletes in the original tables, including writes from the previous Worker during deployment. The migration backfills existing interactions. It stores identifiers and timestamps, not copied comment bodies or precomputed permissions. It is neither an audit log nor a background event system. A failed index update rolls back its originating mutation.

Reads seek by recipient and date, choose at most 21 visible logical events, then hydrate the 20-item page and its like counts. Like groups keep their place in the timeline (migration 0029): the insert trigger adds a like to the recipient's newest source only when that is a like on the same post; anything in between starts a new group with its own event key. A post's first group keeps `likes:<post>` and later groups add a random 12-hex suffix, so every key for a post sorts within `likes:<post>` to `likes:<post>.`; like deletion and the `more` flag seek that range through the group index. `more` marks a group with an older visible group on the same post, so the newer row reads “3 more people like your photo.” Grouping is decided when the like is written, against the newest stored source regardless of later visibility: deleting or hiding the item between two groups leaves them separate and adjacent. Existing groups from before 0029 keep their keys and read state. A like group uses its newest currently visible actor; ties select one actor deterministically. Blocking the latest liker or disabling their membership can move the group backwards immediately. The optional requests filter uses its own indexed ordering. Cursors retain the existing timestamp/key format; concurrent new activity can move a group, and refreshing starts from current state.

Migration 0018 adds one read-state row for each live source, with an autoincremented version that is never reused after deletion/recreation. Insert/update triggers and delete cascades keep it atomic with the original interaction, including mutations from the preceding Worker. The migration imports historical `notification_read` watermarks once; that legacy table remains for compatibility and account-deletion cleanup, and is not consulted or written after backfill.

Migration 0020 adds follower sources when a request becomes accepted or an accepted relationship is inserted. Invitation follows are established before onboarding finishes; their alerts wait until both required avatars exist. Completing photo setup then notifies both participants once. Profile edits, photo replacement, and repeated acceptance do not replay an alert. Existing accepted follows are not backfilled. Removing the relationship deletes its source, receipt, and pending pushes; hidden actors and incomplete profiles are excluded on reads and delivery. A later follow gets a new version, so old receipts cannot clear it. Events use the acceptance/completion time rather than the original request time and link to the follower's current username.

The migration rebuilds the source table to expand its constrained event kinds, preserving exact read versions, read state, queued deliveries, and the receipt sequence high-water mark in the same atomic batch. Seeded D1 tests verify preservation, foreign keys, rollback after failure, and subsequent writes. See setup for release sequencing; this migration must never run opportunistically during requests.

All activity types use the same logical key, visible version, unread flag, badge count, and acknowledgement API. A like group’s version is the maximum version among currently visible sources. Reading clears only visible sources through the supplied version, after verifying that exact source belongs to the caller and is still visible. This is idempotent, handles timestamp ties, and cannot clear a newer like or a cancelled-and-recreated request. Read state does not resolve follow requests. Removed likes, comments, requests, and posts cannot leave accessible orphan notifications; source deletion cascades receipt cleanup, while current membership/block/publication predicates remain authoritative for hidden sources.

The badge counts distinct visible unread event keys and stops at 100 for a 99+ display. Its partial index excludes read history. Acknowledgements are bounded to 20 validated key/version pairs and seek those source groups explicitly; CROSS JOIN preserves that order so SQLite cannot scan the recipient’s entire history for every receipt. Page queries never write. Larger visible like groups and runs of hidden unread actors still require work proportional to those sources; monitor that distribution (see the [scaling watchlist](../../../../docs/scaling-watchlist.md)). Receipts add a row and index writes per interaction, but no hosted service or background job.

The October 12 local D1 regression uses 30 and 3,000 owned posts with a like and comment each. Both sizes used 286 rows read for a 20-item page, 360 for acknowledging that page, and 5 for a badge check with one unread source after the rest of the history had been read. These synthetic row counts do not establish production latency; limits in the tests guard against lifetime scans. The October 11 historical benchmark preceded this read-state model.

[Web Push](../push/README.md) uses the same recipient, logical key, source version, grouping, and read state. Its dispatcher asks this feature to validate current visibility and unread state before sending. A validated focus key can start a page at an older visible event; absent/hidden targets fall back to the current page without disclosing another user's activity. Page reads and push receipt never acknowledge items. Subscription and delivery failure behavior belong to the push feature.

Migration 0023 adds `joined` events for invitees: people who join through an invite link (its owner is the inviter) or an event link (the event creator is the inviter). A new membership records pending completion; the first successful avatar insertion atomically publishes the inviter's activity source and consumes that pending flag. Photo replacements, reinsertions, profile edits and sign-ins never replay it. Completion while blocked/inactive consumes the flag without an alert. Existing members are not backfilled. Membership/block/photo visibility is rechecked on reads, receipts and push, without requiring a follow relationship; the immutable invitation tree establishes the event recipient. Personal invitees may also produce the existing follower event, while shared invitees do not automatically follow anyone.

The table rebuild preserves sources, exact receipt versions/read states, queued push attempts/leases, and sequence high-water marks atomically. A failing migration batch rolls back all changes. New clients explicitly request joined events in list/count reads; older open clients continue receiving only the event kinds they understand. This capability affects rendering compatibility, not authorization. The new row links to the current profile and uses the normal private avatar endpoint.

Migration 0026 adds follow-back dismissal to each existing source receipt, defaulting to undismissed without changing versions or read state. The bounded Activity page checks the outgoing relationship and dismissal in the same query; any pending or accepted outgoing follow hides the prompt. Only follower events qualify. The authenticated dismissal mutation validates the exact visible source version and recipient, is idempotent, and leaves read state unchanged. Removed sources cascade dismissal cleanup; a later new follow receives a fresh prompt, and a delayed dismissal cannot hide it. Actual follow requests continue through the people feature’s authorized, retry-safe mutation. No browser persistence or additional per-item API requests are introduced. Apply migration 0026 before deploying this code; earlier code can run with the added column.

Migration 0030 rebuilds the source table with the same 0023 procedure (preserving sources, exact receipt versions and read state, queued push, and the sequence high-water mark) to add `event_response` and `event_message` kinds. Every trigger that names the table is recreated with explicit column lists, and the push-enqueue trigger now compares session expiry in Better Auth’s ISO text format. Event keys identify their source like comment keys do: `event_response:<event>.<member>` and `event_message:<message>`; no event column is stored. Triggers notify hosts of each guest’s current answer (changing it is a new version; re-saving the same answer is not), every message the other hosts, and host messages (including update blasts) and cancellation everyone who answered. Detail edits are silent; historical `changed` messages are excluded by the common visibility predicate from pages, counts, focus, acknowledgement and push eligibility. Deletions seek each recipient’s key. Reads show event activity only while the event is published, its creator is active and unblocked by the recipient, and the recipient still hosts or answered. Pages return the event ID and title, the actor’s name, the answer, or the message kind and text. List and count reads include event kinds only when the client sends `includeEvents=1`. Members without a profile photo can read Activity so people who joined through an event receive its updates.

Migration 0038 (automatic) rebuilds the source table with the same procedure, now also preserving queued email (a host's versionless blast copy is never cascaded, so it stays in place), to add `host_invite` and `host_accepted` kinds. Triggers on `event_host_member_invite` keep them in step with invitations. The invited member's `host_invite:<event>` names the inviting host as actor; each new invitation is a new version, and one sent after the member declined that event (`event_access.hosting_declined_at`, set by the events feature) is inserted already read, so it raises no badge, push or email. Deleting the invitation removes the notification unless the member now hosts. Acceptance deletes it after inserting the host, so the row stays, read, as the record of hosting, and the same trigger adds `host_accepted:<event>.<member>` for the inviting host (accepting again later is a new version). Leaving or losing hosting deletes the member's record. An open invitation is visible only while it could be accepted (its sender still hosts, both stay connected, the link version is current, and the event is neither cancelled nor over), so a stale row never offers actions that would fail on recheck; the hosting record and `host_accepted` are visible while the relevant members host. Pages add `hosting` (whether the invitation was accepted). List and count reads include these kinds only with `includeHosting=1`. The previous Worker's visibility predicate rejects them, so it neither shows nor delivers them. Triggers write activity only for members, so an invitation write never fails on its notification. `tests/events.test.ts` covers retries, withdrawal, acceptance, leaving, decline and quiet re-invitation, queued email and older clients; `tests/hosting-activity-migration.test.ts` (temporary) covers preservation across the rebuild.

## New-photo alerts

Migration 0039 (automatic) rebuilds the source table with the same procedure as 0038 to add the `post` kind: an alert that a followed member published a photo. It is push and email only. Every Activity read (page, badge, focus) excludes it whatever kinds the client asks for, and `validNotificationKey` rejects `post:` keys, so it can't be focused or acknowledged; it stays unread, which is what push and email require. The category is off by default for both channels.

A trigger on publication (`post.state` becoming `published`) inserts `post:<post>` with the author as actor for each active, unblocked, accepted follower who wants it by email, or by push and has a subscribed device. Members who keep the default write nothing, so the fan-out is proportional to opted-in followers. The usual receipt triggers then queue push at once and email after ten minutes. Delivery rechecks the accepted follow, the post being published by that author, membership and blocks, so unfollowing, deleting the photo, or blocking before delivery suppresses it. Alerts read “alice posted a photo.” with the caption as the quote and open the photo; the service worker opens `#post/<id>` for these keys instead of Activity. Publishing starts the push dispatcher. Since the rows are never read, the 15-minute cron deletes post sources older than two days (after their queues have expired) through a partial index, at most 1,000 per run, cascading their receipts. Until then the badge skips at most two days of a member's post alerts among their unread receipts; see the [scaling watchlist](../../../../docs/scaling-watchlist.md). The previous Worker's visibility predicate rejects post rows, so during deployment it neither shows nor delivers them. Tests in `tests/notification-preferences.test.ts`, `tests/push.test.ts` and `tests/push-worker.test.ts` cover opt-in, exclusion from Activity, email and push text, suppression and cleanup; `tests/post-alerts-migration.test.ts` (temporary) covers preservation across the rebuild.

## Preferences, alert text, and email

Members choose push and email per category in Settings → Notifications. Categories (`src/shared/notification-categories`) name Activity kinds, except that event messages split into ordinary messages, update blasts and cancellations. Migration 0037 stores defaults in `notification_category`, which match earlier behavior: push for everything except likes, and email only for update blasts. Migration 0038 adds co-host invitations (push and email, since they're rare and time-sensitive) and accepted invitations (push). Migration 0039 adds new photos from people you follow (off for both). Migration 0040 turns on email for cancelled events, since guests who joined through an event link often have no push; members who saved a choice keep it. Activity always shows everything except new-photo alerts, which exist only as push and email. `notification_preference` holds only a member's saved choices, and `GET`/`PUT /api/notifications/preferences` reads and saves one category at a time. Preferences only choose alerts, except that new-photo alerts are written only for members who want them.

Triggers on `activity_read_state` queue push (per subscription) and email (`email_delivery`, per member) only for categories the recipient wants, in the same transaction as the activity. Delivery rechecks the preference again at send time, so a change takes effect for queued alerts as well. Like alerts wait 15 minutes. A pending like alert absorbs later likes in its group without being postponed, so a burst becomes one alert (“alice and 3 others like your photo.”). Other email waits 10 minutes and is dropped if the activity was read in the app first. Update blasts and cancellations email at once, and update blasts go out whether or not they've been read; the sending host also gets a copy (`email_blast_copy`, a row with no version). Comments, messages and blasts are individual notifications and are not grouped. Instead, each logical notification alerts at most once an hour per channel (`notification_alert`): another version of the same notification within the hour, such as a re-sent follow request, a changed RSVP or a growing like group, stays in Activity without another alert. Other devices still receive the same version.

`describeNotification` uses Activity's visibility predicate to recheck one notification for delivery and returns its category, the member's choices, its current unread state, and the details for `notificationText`. Push alerts and emails therefore describe the activity, using the same wording as the Activity rows. They include names, event titles and up to 160 characters of comment or message text in push, and the full text in email. A delivered alert can't be recalled after a later block, deletion or sign-out; opening it reauthorizes.

Email (`email.ts`) sends one SES message per recipient, at most 20 per pass, after notifying event mutations and from the minute cron. Delivery is at most once: only a definite SES rejection is retried (after one and then ten minutes, three attempts). A timeout, a full daily budget, or a pass that stopped mid-send ends the row, and rows older than a day are dropped rather than sent late. The email transport caps notification email at 30 per member and 5,000 overall per UTC day, separately from sign-in email. Each email links to its target and carries an unsubscribe link for its category. The token is the member ID and category with an HMAC under `AUTH_SECRET`. `#unsubscribe/<token>` asks for confirmation (mail scanners open links), and the `List-Unsubscribe` header points mail providers' RFC 8058 one-click POST at `/api/unsubscribe/<token>`, which the composition root exempts from its origin check. Either turns off email for that category only and keeps its push choice; GET never changes anything. Rotating `AUTH_SECRET` invalidates outstanding links. Account deletion removes preferences and queued email.

Accepting a follow request still records the new follower with Follow back, but as already read: the accepter neither gets an alert about their own action nor sees their badge rise (the trigger change in 0037). Tests in `tests/notification-preferences.test.ts`, `tests/push.test.ts`, `tests/events.test.ts` and `text.test.ts` cover defaults, validation, enqueue by preference, like coalescing, unread-only email, the hourly cooldown, forged and one-click unsubscribe, account deletion, and the host's copy.
