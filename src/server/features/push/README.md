# Web Push

Push is optional and uses the same recipient, logical event key, and source version as Activity. An active member (including one without a profile photo who joined through an event) explicitly registers a browser subscription in Settings (or optional device setup in previously loaded clients). Each member has at most ten subscriptions. A session can own multiple endpoints because iOS can copy one login cookie into isolated installations. Endpoints stay unique and cannot be adopted by another account or session. Indexed conditional writes enforce the cap and ownership even under concurrent retries. Endpoints must be HTTPS on recognized browser push providers; redirects are never followed. Encryption keys are validated before storage. Subscription APIs are private, same-origin, and scoped to the current server-issued session and exact browser endpoint. Missing local subscriptions return no enabled registration; the endpoint is supplied in a header rather than a URL. `hasPushSubscription` reports whether a member has any subscription with an unexpired session; bootstrap uses it so an iPhone browser tab can skip Home Screen guidance once push works elsewhere. Disable removes only that endpoint. Sign-out revokes all installations sharing the same login session, while other sessions remain independent.

Migration 0019 enqueues delivery in the same transaction as an unread activity receipt. Failed enqueue rolls back the interaction. No existing activity is replayed on opt-in. One pending item per subscription/event coalesces a newer version of the same alert, such as a re-sent request. Likes never enqueue alerts (migration 0029 removed them from the trigger and dropped queued like deliveries); they appear only in Activity, and like routes skip opportunistic dispatch. Reading or deleting a source cancels queued work. Repeated registration of identical keys preserves pending work; changing an existing endpoint’s encryption keys discards its previous queue. A new endpoint is independent; disabling an old endpoint removes its queue, and expired provider endpoints are removed on a 404/410 response. Sign-out/session deletion and inactive membership cascade subscription removal. Expired sessions cannot receive pushes and existing auth maintenance removes them.

Successful relationship/interaction mutations, avatar completion, and event answers, messages, explicit host notifications, and cancellation start a best-effort dispatcher. Detail edits, event reads, link opening/preview, cover uploads, and host management do not start dispatch. An hourly cron on the same Worker recovers missed dispatches and retries. Work that becomes eligible after immediate dispatch, such as a retry, waits for another eligible successful mutation or the next hourly pass. An idle backlog drains at most five deliveries per hour, so delays can exceed an hour when more work is queued. Indexed cleanup removes at most 100 expired and 100 exhausted items per run. An atomic claim leases five deliveries for 60 seconds; version/lease conditions protect newer activity from stale completion. Send checks current session, membership, source visibility, and unread state. Provider timeouts and temporary failures set exponential retry eligibility (30 seconds to an hour), waiting longer when Retry-After requires it; actual dispatch follows the hourly/opportunistic cadence, with at most eight attempts and a 24-hour queue lifetime. Provider 404/410 removes the exact expired subscription; permanent errors discard the delivery. No hosted queue or paid service is provisioned.

New followers use the same queue and generic alert as requests and comments. Acceptance replaces any queued request with the new follower version. Invitation follows enqueue only after both profile photos exist; existing follows are not replayed. Losing the accepted relationship, profile completion, membership, or block permission before dispatch suppresses delivery.

The maintained `@block65/webcrypto-web-push` package performs RFC 8291 encryption and VAPID signing with Web Crypto in Workers. Stable VAPID keys are Worker secrets; see setup for generation and custody. Payloads contain only notification identity/version and a subscription ID. The service worker shows generic text and reuses a stable notification tag; provider topics also coalesce queued duplicates. Provider acceptance and retries cannot guarantee exactly-once OS delivery. An alert already accepted by a provider cannot be recalled, so names, comments, and photos are never included. Opening it reauthorizes through Activity. Sending or receiving does not mark it read. Read acknowledgement dismisses local alerts, but already delivered alerts on other devices are not remotely dismissed.

Tests use real isolated Workers/D1, synthetic sessions, simulated provider responses, independently decrypted payloads, and verified VAPID signatures. They cover explicit opt-in, privacy, duplicate mutations, concurrent claims/newer events, failures, revocation, expiry, and restore quarantine. Event integration tests verify immediate dispatch without cron for answers, messages, explicit host notifications, and cancellation, including members without profile photos, and suppress retries after read acknowledgement or blocking. Host notification tests cover Activity for guests without push, unchanged retries without replay, silent detail edits, and suppression of historical detail-change alerts. They do not establish delivery to an actual device or test browser UI.

Invitee-completion events also use the existing generic opt-in alert, outbox, version checks, and profile-authorized Activity destination. Avatar completion creates the source transactionally; no email activity alert is added, and no existing join is replayed.

Migration 0027 preserves subscription IDs/keys and all queued versions, leases, and retry state while removing the one-subscription-per-session constraint. Apply under maintenance with the matching Worker, as described in setup.md. Old loaded clients retain their current deliveries and may read a sole session subscription, but must reload before enabling/disabling: a session-only mutation cannot safely identify an installation after cookie copying. No stale session-only mutation can revoke or replace another installation.
