# Email delivery

The application sends one-time sign-in links through the Amazon SES v2 API, signing requests with `aws4fetch` using a sending-only IAM user, including those for signing in through an invite or event link. Authentication and membership own credentials; this transport never invents them. Only configured same-origin verification/join links may be sent. No links, tokens, recipients, or email bodies are logged. Login mail retains generic responses when throttled.

D1 reserves at most three delivery attempts per recipient per UTC hour; failed or throttled attempts consume reservations. There is no application-wide daily cap: total spending is capped by an AWS budget action that blocks the sending user (see [SES setup](../../../docs/setup.md#amazon-ses)), so a cap breach appears here as failed deliveries. SES has no idempotency key, so the transport never retries; a failed or timed-out request reaches the member as an error, and a later request may deliver a second equivalent link. Recipient budget keys use a hash and expire after two days. These records are operational throttles, not analytics. Better Auth also enforces per-IP request limits in D1.

Addresses without an account or working invite or event link receive an explicit invitation-required error without a delivery. The optional reply-to inbox can differ from the sending domain. SES adds no open or link tracking because no configuration set is used. SES failures log only the HTTP status and AWS error type, because SES error messages can contain addresses. The provider will necessarily process recipients and email contents, so the production privacy notice must describe this. Production delivery and sign-in through SES are verified; tests use a simulated SES boundary that requires a SigV4 signature and send no real email.

[Notification email](../features/notifications/README.md) uses `sendNotificationEmail`: one message per recipient with `List-Unsubscribe` and one-click `List-Unsubscribe-Post` headers, whose unsubscribe link must be same-origin. It never uses the sign-in budget, so it cannot block sign-in; instead it reserves daily budgets of 30 per recipient (keyed by address hash) and 5,000 overall, returning `throttled` when either is full. The result distinguishes a definite SES rejection from a timeout or network error that may have delivered, so callers retry only the former. Subjects that aren't 7-bit ASCII, such as names with accents or emoji, are sent as RFC 2047 encoded words, as SES requires. Notification email carries member-written names, event titles, comments and messages, so the privacy notice must cover SES processing them too.

The email module owns scheduled cleanup of expired budget records, bounded to 100 records per pass; the composition root only invokes it.
