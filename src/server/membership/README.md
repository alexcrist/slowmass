# Membership and invitations

Membership is separate from an authenticated identity. A verified email can join only through an unexpired invitation issued by a currently active member. Active means membership status is `active`, not a recent activity score. The first verified account matching the operator's bootstrap email is the only root; a database constraint prevents a second root.

Personal invitations are tied to exact normalized email addresses. Shared invite links issue an email-bound redemption only at verified membership creation. Normalization trims whitespace and lowercases; it does not merge aliases. Membership owns the eligibility record; the invitations feature delivers the invitation email through the shared email transport. Invitations expire after seven days, with no daily issuance limit per member. Retrying an outstanding invitation does not create another record. Shared email-delivery budgets still apply.

Accepting a personal invitation link credits that specific inviter, even if another invitation is older. Normal email sign-in without a specific invitation credits the oldest still-valid one. Joining inserts membership and consumes that invitation atomically through D1 triggers. The insert rechecks the credential hash, recipient email, current inviter status, expiry, revocation, and absence of prior membership. A join link cannot authenticate an existing member, including after joining through another invitation or the regular login flow. Membership retains inviter, invitation, and join time; provenance cannot be rewritten. Disabling an inviter before acceptance invalidates pending invitations. It does not automatically disable existing descendants. Bulk-ban functionality is not implemented.

Invitation and membership records must survive account cleanup as minimal tombstones so descendant attribution remains available. Delete personal profile/email content separately; do not cascade-delete the invitation graph. `membership_inviter` supports future descendant traversal. Status exists to enforce eligibility, not as a completed moderation interface.

The auth module uses these rules during user/session creation. Every private application endpoint must additionally require current active membership. Integration tests exercise joining, provenance, and revoked eligibility against local D1.

For personal email invitations, inviter and invitee automatically follow each other once both have profiles. The initial-profile trigger checks both members are active and neither has blocked the other. Profile edits and subsequent sign-ins never recreate removed relationships. This applies when completing a profile after migration 0011; existing completed pairs are not backfilled. The personal invitation UI discloses the mutual connection.

Shared links use library-generated entropy and retain a lookup hash. A temporary claim binds the hash of the library-owned magic-link token to the inviter, exact credential version/hash, normalized email, and redemption ID. Only the library’s validated verification endpoint uses this claim; caller-supplied metadata grants eligibility to request email, never authentication. The identity hook checks that claim before creation. The session hook inserts the email-bound shared invitation and membership through one conditional batch. Existing active members retain their original provenance and create no new invitation.

The conditional batch and membership validation triggers enforce the exact claim/version/hash, expiry, revocation, verified email, active inviter with a profile photo, and one membership under races. Successful joins retain an immutable personal/shared invitation type and their inviter/timestamps; rotating or expiring a shared credential never changes this provenance. Shared invitations are excluded from personal-invitation eligibility, email history/delivery, and automatic follows. A failing shared claim cannot fall back to another invitation. Two valid links racing for the same member preserve the first inserted membership. Shared links have no capacity field or consumption counter.

A committed membership survives a session/response failure; ordinary email sign-in recovers it. A failed join can request another verification email through a valid current shared link. Claims remain until ten-minute expiry even if the shared credential expires or changes first, preventing fallback while the library email token remains usable. Bounded scheduled cleanup then removes claims; they retain neither raw verification tokens nor sessions. Both writes and the database trigger recheck the credential and inviter, including for already-sent emails. Auth fixes the selected shared source before email-token consumption and retains it across identity/session hooks, rejecting membership if cleanup removes the claim during verification.

Accepted membership does not depend on completing onboarding or retaining the original invitation. A returning active member can request a fresh ordinary email sign-in after session loss, even if the shared link is revoked or the inviter is subsequently disabled. Bootstrap returns a missing profile or `hasAvatar=0` until setup is complete; client onboarding gates precede all main-app routes, with server-side completion checks on member features. Saved identity survives an interrupted photo step. Regression tests cover both invite types, repeated session loss at both steps, unchanged attribution, and completion unlocking the feed.

Request authorization reads active membership and profile-photo completion in one indexed query. A missing or inactive member returns no access; a member without a photo remains signed in but cannot use completed-member features. This result is request-local and does not replace domain-level checks inside mutations.
