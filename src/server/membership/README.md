# Membership and admission

Membership is separate from an authenticated identity. Apart from the first verified account matching the operator's bootstrap email—the only root, protected by a unique index—a verified email joins only by signing in through an invite link or an event link from an active member with a profile photo. Active means membership status is `active`, not a recent activity score.

Every join retains its inviter, invitation, and join time; provenance cannot be rewritten. A link join holds a `shared` invitation that records the exact link version used: `invite_link_id` for an invite link (the owner is the inviter), or `event_id` and `event_link_id` for an event link (the creator is the inviter). Together with legacy `personal` email invitations and the root, this identifies every member's entry source, so joins can be counted per link version to trace and shut down mass sign-ups (see the [operations runbook](../../../docs/operations.md#join-sources-and-shutting-down-bot-sign-ups)). Invite-link joins from before migration 0030 have no recorded version. Invitation and membership records survive account cleanup as minimal tombstones so descendant attribution remains available; delete personal profile/email content separately and never cascade-delete the invitation graph. `membership_inviter` supports descendant traversal. Status enforces eligibility; there is no moderation interface or bulk ban. Disabling an inviter stops their links from admitting anyone but does not disable descendants.

Personal email invitations were removed when events shipped. Their records remain; migration 0030 revoked outstanding ones, along with that day's invite links. Members who joined through a former personal invitation still follow their inviter automatically when both create profiles (the initial-profile trigger checks active membership and blocks); invite and event links create no follows.

Both kinds of link use the 48-character credentials and SHA-256 lookup hashes in `credential.ts`, and the same sign-in pattern. The magic-link sender binds a four-hour claim to the email token, pinning the exact link version. Google initiation pins a ten-minute claim before the email is known, carries its handle through library-protected server state, and fills its email only after provider verification. Both flows use the same admission batches and constraints. Verification rechecks the claim inside one batch and inserts the invitation and membership; membership validation triggers enforce the exact claim, link version, owner, and expiry under races. A claim never falls back to another source: it remains until expiry even if the link changes, and a changed or closed link rejects pending new people. `claimSource` tells auth which kind of claim an email token carries, before the library consumes it. A committed membership survives a session/response failure; ordinary email sign-in recovers it.

## Invite links

`invite.ts` decides whether an invite link admits new people and joins them. A link admits people while it is unexpired and unrevoked and its owner is active with a profile photo. Only new people get a claim; members signing in through a link sign in normally and keep their attribution. The [invite-links feature](../features/invite-links/README.md) issues and renews links.

## Event admission

`event.ts` decides who may open, answer, or join through an event, because email verification shares those rules.

- **Signing in through a link.** Members may bind through any working link to view the event; new people only while it admits them (published, not cancelled, not over, creator active with a photo). Invalid or closed links send no email. For everyone, verification records an access row with the link version. Only restore quarantine changes an event's link version.
- **Opening a link while signed in** records the same access row. The events feature also records current-link guest access when a host invites an existing connected member to co-host; this never creates a membership or changes join attribution. Access lets a member view the event only while its link version is current. Hosts need no row.
- **Answering** requires an active member with a profile who is not blocked with the creator, while the event is open. Hosts may always answer; anyone else must have answered already, or have opened the current link while the event has under 500 answers (bounding notification fan-out; hosts are capped separately at ten). An unchanged answer keeps its timestamp. Answers survive a link version change.

New members give only a name afterward; the people feature generates their username. Request authorization reads active membership and profile-photo completion in one indexed query; members without a photo stay signed in but can use events, Activity, push, profile naming, photo upload, account deletion, discovery, and other members’ identity/avatar previews. Following, posting, and the feed remain gated on photo completion. That result is request-local and does not replace domain checks inside mutations. Integration tests (`tests/invite-links.test.ts`, `tests/events.test.ts`, `tests/worker.test.ts`) cover joining through both kinds of link, recorded link versions, renewed, revoked, and expired invite links, changed event link versions, cancelled events, disabled or photo-less inviters, races between links, rolled-back joins, revoked legacy invitations, immutable provenance, and the single root against local D1.
