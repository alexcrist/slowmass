# Membership and event admission

Membership is separate from an authenticated identity. Apart from the first verified account matching the operator's bootstrap email—the only root, protected by a unique index—a verified email joins only by signing in through an event link from an active member with a profile photo. Texting an event's URL is the only way to invite someone. Active means membership status is `active`, not a recent activity score.

Every join retains its inviter, invitation, and join time; provenance cannot be rewritten. An event-link join holds a `shared` invitation from the event creator that records the event and the exact link version used, so joins can be counted per link version to trace mass sign-ups. Invitation and membership records survive account cleanup as minimal tombstones so descendant attribution remains available; delete personal profile/email content separately and never cascade-delete the invitation graph. `membership_inviter` supports descendant traversal. Status enforces eligibility; there is no moderation interface or bulk ban. Disabling an inviter stops their links from admitting anyone but does not disable descendants.

Email invitations and invite links (migrations 0014–0025) were removed. Their records remain; migration 0030 revoked outstanding ones. Members who joined through a former personal invitation still follow their inviter automatically when both create profiles (the initial-profile trigger checks active membership and blocks); event links create no follows.

## Event admission

`event.ts` decides who may open, answer, or join through an event, because email verification shares those rules. Event links use the 48-character credentials and SHA-256 lookup hashes in `credential.ts`.

- **Signing in through a link.** The magic-link sender binds a ten-minute claim to the email token, pinning the exact link version. Members may bind through any working link to view the event; new people only while it admits them (published, not cancelled, not over, creator active with a photo). Invalid or closed links send no email. Verification rechecks the claim inside one batch: for new people it inserts the invitation (event and link version) and the membership; for everyone it records an access row with the link version. Membership validation triggers enforce the exact claim, link version, creator, and expiry under races. A claim never falls back to another source: it remains until expiry even if the link version changes (only restore quarantine does that), and a version change or closing rejects pending new people. A committed membership survives a session/response failure; ordinary email sign-in recovers it.
- **Opening a link while signed in** records the same access row. Access lets a member view the event only while its link version is current. Hosts need no row.
- **Answering** requires an active member with a profile who is not blocked with the creator, while the event is open. Hosts may always answer; anyone else must have answered already, or have opened the current link while the event has under 500 answers (bounding notification fan-out; hosts are capped separately at ten). An unchanged answer keeps its timestamp. Answers survive a link version change.

New members give only a name afterward; the people feature generates their username. Request authorization reads active membership and profile-photo completion in one indexed query; members without a photo stay signed in but can use only events, Activity, push, profile naming, photo upload, and account deletion. That result is request-local and does not replace domain checks inside mutations. Integration tests cover joining, recorded link versions, changed link versions, cancelled events, disabled creators, revoked legacy invitations, immutable provenance, and the single root against local D1.
