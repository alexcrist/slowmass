# Authentication

Better Auth owns one-time email links and signed cookie sessions; D1 stores its schema and request-rate counters. No passwords or social login providers are enabled. Normal sign-in links expire after ten minutes, are stored hashed, and can be consumed once. Verification creates an email-verified identity before session issuance.

Invitation emails additionally carry seven-day, join-only credentials. The `invitation-join` Better Auth plugin previews them without consumption and accepts them only through an explicit same-origin POST. Membership's conditional insert consumes the specific invitation atomically; only that winning request may ask Better Auth to create a session and set its signed HTTP-only cookie. Better Auth generates credential entropy and owns identity/session creation and cryptography. A SHA-256 hash is indexed in D1; the credential is placed in the email URL fragment and sent only in request bodies, keeping it out of HTTP URLs/referrers and application logs. The API never gives the inviter a credential. Preview and acceptance share a ten-requests-per-IP-per-minute library limit.

Used, expired, cancelled, inactive-inviter, and already-member invitations cannot create sessions, even if another invitation is still valid. Normal email sign-in joining also invalidates all join links for that recipient. An existing session must be explicitly signed out before accepting an invitation for another account. Incomplete identity creation can be retried; if membership succeeds but session issuance or the response fails, normal ten-minute email sign-in recovers access. This deliberately does not turn an old invitation into a reusable login link. No frontend callback or submitted email can change the credential's recipient.

[Membership](../membership/README.md) is required during user/session creation and on private API reads/writes. Verification also checks that an invitation's issuer remains active. A narrowly configured first-member bootstrap establishes the root of the invitation tree.

Link requests for addresses without active membership or a valid invitation return `403 INVITATION_REQUIRED` without sending email. Expired, revoked, and inactive-inviter invitations are ineligible. This deliberately reveals sign-in eligibility to make onboarding clear, but does not distinguish existing members from invitees or disclose inviter details. The same origin checks and library rate limits apply. Eligibility is checked again when verifying a link; a successful request never grants membership by itself.

Missing credentials fail closed. Session cookie caching is disabled so invalidation reaches D1. Development uses localhost cookies; production requires secure cookies and a separate auth secret. Mutation origin checks supplement library protections. Production uses Cloudflare's client-IP header for request throttling. Library responses retain the Worker's security and private/no-store headers, including errors and verification redirects, while preserving session cookies.

Library logging retains event level only because database exceptions may contain credential parameters. Request IDs, route names, status, and timing come from the Worker's sanitized telemetry; do not enable raw auth error logging in production.

`options.ts` owns library configuration and lifecycle hooks; `index.ts` creates the library instance; `invitation.ts` integrates invitation acceptance through the library's plugin API. Worker integration tests exercise email-link and invitation issuance, verification, cancellation, races, and session creation through a simulated outbound email transport. They do not send real email or prove hosted deliverability.

Auth owns bounded cleanup of expired sessions and verification records. Missing provider configuration returns service-unavailable responses rather than telling a mounted client that its session expired.

`getActiveSession` exposes the authenticated server session ID alongside the existing active-user identity for device push ownership. Deleting a session cascades its push subscription and queued deliveries; delivery also checks session expiry before sending.

## Workers initialization and recovery

Wrangler aliases Better Auth's async-hooks loader to a small static `node:async_hooks` import. The installed library otherwise caches a dynamic-import promise at module scope; [upstream issue 10315](https://github.com/better-auth/better-auth/issues/10315) reports that an interrupted Workers request can leave subsequent authentication waiting on that promise. This is a mitigation for a matching failure mode, not a reproduced diagnosis of Slowmass's production stalls. Remove the adapter when a verified upstream release provides the equivalent Workers-safe import; the integration bundle check guards against reintroducing the dynamic import. Test builds read the same Wrangler alias.

Only fully initialized library instances are reused. An unfinished initialization never becomes the shared instance. Session-library operations have an eight-second deadline, and auth HTTP handlers have twenty seconds to allow email delivery. Expiry evicts the affected cached instance and produces a private retryable 503, never a false signed-out response. A timed-out initialization cannot subsequently start the requested action. An already-running mutation may finish after a deadline and is never automatically replayed. Membership/profile reads remain independently authorized; client startup has its own deadline for the complete response.

Request-time database schema inspection is disabled. Better Auth 1.7.7 starts it without awaiting completion of initialization and caches its pending verdict; a cancelled request can strand later requests on that verdict ([upstream issue 11651](https://github.com/better-auth/better-auth/issues/11651)). Schema validation instead runs explicitly against migrated, isolated D1 in CI. The regression holds a real library schema query, verifies a second legacy session lookup stalls, and verifies normal session authentication no longer depends on that query. A second check deliberately removes a required column to prove schema drift fails validation. This changes schema introspection only: signed sessions, membership checks, origin checks, and rate limits remain enforced. It is a mitigation for a reproduced library failure mode, not a confirmed diagnosis of a specific production request.

`auth.timeout` records only the phase (initialization, session read, or handler). Combine it with request telemetry to distinguish a pending database operation from initialization that has made no database call. Cancellation/concurrency tests use isolated Workers/D1 and synthetic sessions; controlled library-boundary failures cover deadlines, cache recovery, and HTTP 503 behavior. They do not reproduce the provider-specific interrupted-import fault.

Shared invitations use the existing Better Auth magic-link plugin for email proof and session cryptography. The sender callback validates `metadata.inviteLink` and stores a short-lived claim pinned to the current credential version/hash before sending; raw credentials are never logged. The library consumes its one-time token before user/session hooks redeem the claim. A pre-verification hook fixes the selected invitation type for the request before token consumption; identity/session hooks retain that classification. Removing an expired claim during verification cannot switch attribution to a personal invitation; membership still requires a valid current claim. Claims pin attribution independently of cookies and callback parameters, supporting email browsers and installed-app paste flows. Existing active members use normal sign-in and retain provenance. Expired/replaced/revoked shared credentials do not fall back to personal invitations; their claims remain until the email token’s lifetime ends. The shared preview is a read-only, rate-limited POST and cannot authenticate anyone. Missing/failed eligibility yields safe errors and the join page offers a new email request. Restore quarantine clears claims and revokes current shared links alongside personal join credentials.

Session/user reads use Better Auth’s native D1 join. Active membership and profile-photo completion are read together on every request; neither is cached between requests. Member routes consume that completion result, while domain queries retain their current publication, follow, block, and ownership checks. The isolated D1 regression verifies the joined read count and immediate changes to completion, membership, and session expiry.
