# Authentication

Better Auth owns one-time email links, Google OAuth redirects, and signed cookie sessions; D1 stores its schema and request-rate counters. Google is configured only when both provider credentials are present; its backend and sign-in UI are implemented; the identity migration and hosted rollout are complete, while completed real-provider sign-in verification remains pending. No passwords are enabled. Normal sign-in links expire after four hours, are stored hashed, and can be consumed once. Verification creates an email-verified identity before session issuance. The [shared sign-in contract](../../shared/sign-in/README.md) keeps token expiry, claim lifetime, email text, and client instructions aligned. Existing links retain their originally stored expiry; no migration extends them.

Invite links and event links are the invitations. Their credentials use 48 random characters with hashed lookup. Member invite links retain fragment URLs; event links use a server-visible path for title/cover-only previews, with older fragment links still supported. Interactive invitation checks send credentials in bodies. No-referrer responses and sanitized application logs limit disclosure; hosting infrastructure and link-preview providers necessarily receive shared event URLs. Signing in through one uses this same magic-link flow: `metadata.inviteLink` or `metadata.eventLink` binds a membership-owned claim to the email token before sending, pinned to the exact link version. Invite links bind claims only for new people; event links also bind them for members, to record that they opened the event. A pre-verification hook records which kind of claim the request carries before the library consumes its token, and identity/session hooks keep that classification: cleanup removing the claim mid-verification fails rather than falling back. User creation for a new email requires a valid claim of that kind for that email; session creation inserts new people's invitation and membership, and for event links records the member's access through that link version. Claims pin attribution independently of cookies and callback parameters, supporting email browsers and the installed-app paste flow. Newly issued emails use a local failure destination carrying the original invite/event credential in its fragment, without the email address or verification token. That destination is encoded in the email verification URL’s query, so the email provider and hosting infrastructure handling verification also receive the invitation credential; application logs remain sanitized and responses use no-referrer. Better Auth’s invalid/expired-token redirects and the auth adapter’s failed-verification fallback preserve this recovery context. Resending rechecks current eligibility and binds a fresh claim to that same source; recovery parameters grant no membership or session. Older emails without this context require reopening the original invitation to join.

[Membership](../membership/README.md) is required during user/session creation and on private API reads/writes. A narrowly configured first-member bootstrap establishes the root of the invitation tree. If membership succeeds but session issuance or the response fails, normal four-hour email sign-in recovers access.

Link requests for addresses without active membership, a working invite or event link, or the bootstrap configuration return `403 INVITATION_REQUIRED` without sending email; for new people an event must also still admit them. This deliberately reveals sign-in eligibility to make joining clear, without disclosing inviter or event details. The same origin checks and library rate limits apply. Eligibility is checked again when verifying a link; a successful request never grants membership by itself.

Sessions expire sixty days after their last renewal. Renewal extends the D1 row and reissues the cookie, so only `/api/bootstrap`, which every app start calls, renews (at most daily) and forwards the library's `Set-Cookie` headers. Other private reads disable renewal: their responses would drop the cookie, leaving its original lifetime in place. Sign-out, account deletion and membership disablement still end access immediately.

Better Auth stores dates as ISO-8601 text. Raw SQL that compares session or verification dates binds `authDate()`, never `Date.now()`. SQLite orders every number before every text value, so a numeric bound treats every stored expiry as unexpired. Test fixtures write the same text format.

Missing credentials fail closed. Session cookie caching is disabled so invalidation reaches D1. Development uses localhost cookies; production requires secure cookies and a separate auth secret. Mutation origin checks supplement library protections. Production uses Cloudflare's client-IP header for request throttling. Library responses retain the Worker's security and private/no-store headers, including errors and verification redirects, while preserving session cookies.

Library logging retains event level only because database exceptions may contain credential parameters. Request IDs, route names, status, and timing come from the Worker's sanitized telemetry; do not enable raw auth error logging in production.

`options.ts` owns library configuration and lifecycle hooks; `index.ts` creates the library instance. Worker integration tests exercise email-link, invite-link, and event-link sign-in, verification, link renewal and version changes, races, and session creation through a simulated outbound email transport. They do not send real email or prove hosted deliverability.

Auth owns bounded cleanup of expired sessions and verification records. Missing provider configuration returns service-unavailable responses rather than telling a mounted client that its session expired.

`getActiveSession` exposes the authenticated server session ID alongside the existing active-user identity for device push ownership. Deleting a session cascades its push subscription and queued deliveries; delivery also checks session expiry before sending.

## Google and shared account identity

Google uses Better Auth's authorization-code flow, PKCE, state validation, and browser-bound state cookie. Slowmass does not implement OAuth cryptography. The sign-in policy accepts only Google with OpenID/email/profile scopes, rejects direct client ID tokens and explicit account-link/token endpoints, and chooses local success/failure destinations. The controls send `additionalData.inviteLink` or `additionalData.eventLink`; these are untrusted credentials, never admission decisions.

Before redirecting, membership pins a ten-minute claim to the exact invitation/event version, with no email yet. Only the claim handle and source are attached through Better Auth's server-owned OAuth state; client-supplied state fields are discarded. After Google returns, its verified email identifies that claim. Existing user/session lifecycle checks revalidate the invitation and commit membership/access through the same constrained D1 batches as email links. A missing/expired claim or changed invitation cannot fall back to bootstrap or another source. OAuth cancellation does not admit anyone; a retry starts a new flow. Existing members keep their original provenance; blocks still suppress event access.

Google identities need `email_verified=true` and either a consumer Gmail address or a managed Workspace `hd` claim. Google accounts backed by unmanaged third-party addresses use email links to prove current mailbox ownership. Both the local email and provider email must be verified for implicit linking. An already-linked Google subject whose email changes is rejected for recovery rather than reassigned or silently changing the local email. Google profile names/photos never replace app profiles; provider access, refresh, and ID tokens are discarded by persistence hooks. Only the stable provider subject/account binding is retained.

`email.ts` resolves sign-in addresses before issuing an email token or matching a Google identity. Matching trims/lowercases addresses and, only for `gmail.com`/`googlemail.com`, removes local-part dots and `+` tags and uses `gmail.com`. Existing addresses and IDs are preserved; new identities use the canonical address. Workspace/custom domains retain dots and tags. Ambiguous existing matches fail closed and require operator recovery, never automatic merging. Migration 0036 adds indexed canonical uniqueness and unique provider-subject ownership; it is manual because it adds constraints. The read-only audit in the setup guide must pass again immediately before migration. Old pending email links that collide with an account created through another alias may need resending; they cannot create a duplicate identity.

Local integration tests use real Better Auth/Workers/D1 with synthetic Google token responses at the network boundary and a provider-side PKCE check. They cover account reuse in both directions, provenance, event access, collisions, simultaneous callbacks, revoked/expired claims, changed link versions, verified-email policy, disabled members, state cookies/replay, scopes and origin checks. They do not exercise Google's live consent screen or prove hosted login.

## Workers initialization and recovery

Wrangler aliases Better Auth's async-hooks loader to a small static `node:async_hooks` import. The installed library otherwise caches a dynamic-import promise at module scope; [upstream issue 10315](https://github.com/better-auth/better-auth/issues/10315) reports that an interrupted Workers request can leave subsequent authentication waiting on that promise. This is a mitigation for a matching failure mode, not a reproduced diagnosis of Slowmass's production stalls. Remove the adapter when a verified upstream release provides the equivalent Workers-safe import; the integration bundle check guards against reintroducing the dynamic import. Test builds read the same Wrangler alias.

Each auth operation creates a request-local library instance. A completed `$context` does not establish that every lazily initialized object or promise in that instance is safe to reuse after its originating Workers request ends. This replaces the earlier completed-initialization cache after a production session check timed out before any database query. It trades repeated initialization work for isolation; hosted CPU and recurrence still require observation. The auth secret, cookie format, session rows, expiry, and invitation credentials are unchanged, so existing logins do not require a migration or replacement cookie.

Session-library operations retain an eight-second deadline, and auth HTTP handlers have twenty seconds to allow email delivery. Expiry produces a private retryable 503, never a false signed-out response. A timed-out initialization cannot subsequently start the requested action. An already-running mutation may finish after a deadline and is never automatically replayed. Membership/profile reads remain independently authorized; client startup has its own deadline for the complete response.

Request-time database schema inspection is disabled. Better Auth 1.7.7 starts it without awaiting completion of initialization and caches its pending verdict; a cancelled request can strand later requests on that verdict ([upstream issue 11651](https://github.com/better-auth/better-auth/issues/11651)). Schema validation instead runs explicitly against migrated, isolated D1 in CI. The regression holds a real library schema query, verifies a second legacy session lookup stalls, and verifies normal session authentication no longer depends on that query. A second check deliberately removes a required column to prove schema drift fails validation. This changes schema introspection only: signed sessions, membership checks, origin checks, and rate limits remain enforced. It is a mitigation for a reproduced library failure mode, not a confirmed diagnosis of a specific production request.

`auth.timeout` records only the phase (initialization, session read, or handler). Request telemetry additionally records the last session boundary reached: dispatch, endpoint entry, or library session lookup. The diagnostic hook delegates unchanged to Better Auth; it never inspects or records cookie or lookup-token values. Combine these markers with pending database counters to narrow a recurrence. Cancellation/concurrency tests use isolated Workers/D1, real local HTTP aborts, and pre-existing synthetic cookies; controlled library-boundary failures cover instance isolation, deadlines, and HTTP 503 behavior. These tests do not reproduce the exact unresolved production await and do not prove that every hosted stall is fixed.

Session/user reads use Better Auth’s native D1 join. Active membership and profile-photo completion are read together on every request; neither is cached between requests. Member routes consume that completion result, while domain queries retain their current publication, follow, block, and ownership checks. The isolated D1 regression verifies the joined read count and immediate changes to completion, membership, and session expiry.

OAuth failure destinations include `auth=google` so the welcome screen offers Google retry or email without calling an OAuth cancellation an expired email link. This query value controls copy only, never authorization.
