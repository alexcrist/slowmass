# Local image decoding

Avatar and post cropping share type checks and orientation-aware bitmap decoding. Originals may be JPEG, PNG, WebP, or HEIC/HEIF, with no byte or pixel limit of their own: the owner chose letting an oversized photo fail on the device over refusing photos in advance. A photo the device cannot decode in memory shows the could-not-open error or, at worst, crashes the tab. After decoding, an original whose long edge exceeds 4096px is reduced to that size and the full decode released, which bounds what the crop editor holds; if the browser cannot produce the reduced copy, the full-size bitmap is used. The reduced copy is still more than twice the largest upload, so only tight crops of very large photos lose detail.

Both crop editors encode the selected original pixels at up to a 1600px long edge, without upscaling, requesting WebP quality 0.92. They validate the actual encoder output (including a browser’s supported-format fallback) against the 8 MiB upload limit before allowing upload. The server independently validates and re-encodes those bytes; client checks are only for usability. No additional compression pass is needed for larger originals.

## HEIC

HEIC never reaches the server: like every other original it is decoded here, cropped, and uploaded as the encoder's WebP output, so the server's still-format allowlist is unchanged. A file counts as HEIC by its `image/heic`/`image/heif` type, or by a `.heic`/`.heif` name when the browser reports no type. File inputs list both through `PHOTO_ACCEPT`; listing HEIC also means iOS hands over the original instead of converting it to JPEG.

The browser's own decoder is tried first (Safari opens HEIC). If it refuses, `libheif-js` decodes the primary still image in a dedicated worker, created for that one photo and terminated afterwards or when the 30-second decode deadline expires. The worker script is a separate content-hashed file of about 3.2 MB (about 0.8 MB compressed), fetched only when this fallback runs. It uses the package's pure-JavaScript build rather than WebAssembly so the `script-src 'self'` policy needs no `wasm-unsafe-eval`, and a same-origin worker file so it needs no `blob:` worker source.

A HEIC original is decoded once. When a post or event-cover crop is applied, `recropSource` gives the form a JPEG (quality 0.95) of the decoded pixels at the same dimensions, and reopening the crop decodes that instead; other formats reopen from the original. Decoding the original HEIC a second time was reported to fail in use; the cause was not reproduced here and is presumed to be memory. If the copy cannot be made the original is kept. The copy has no alpha channel.

Limitations of the fallback: it is slower than native decoding, ignores embedded color profiles (wide-gamut phone photos can look slightly flatter than in Safari), and reads only the primary still of a Live Photo, burst, or sequence. HEIC rotation is applied by the decoder. Only a small synthetic still is tested, in Node and through the built worker script; real phone photos and browsers are not covered by automated checks. `libheif-js` is LGPL-3.0 and is bundled unmodified.

Callers own bitmap lifetime, close it on replacement/unmount, and ignore late decodes. Files and previews remain in memory. Unsupported or undecodable sources show a recoverable error; the original is never uploaded as a fallback.

Decoding and crop encoding each have a 30-second deadline. A decoder result arriving after expiry is closed, and an expired encoder result is ignored. These deadlines release pending UI when the event loop can run; they cannot preempt a synchronous browser freeze or keep a very large original from exhausting device memory. Both crop editors use the same bounded encoder.

`PhotoProgress` supplies the shared phase/status copy for crop editors and all three upload forms. It shows a byte percentage only while the browser reports sending the photo. After the body is sent, processing and saving remain one unmeasured phase until the server confirms success; there is no invented processing percentage. After 15 seconds in a phase, a polite status explains the longer wait. Progress uses neutral styling and phase announcements rather than repeated screen-reader percentage announcements.
