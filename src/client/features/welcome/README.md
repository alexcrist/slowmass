# Welcome

Shows a neutral loading state until service availability, session, and the current member's profile are known from one private `/api/bootstrap` response. Only a confirmed signed-out response reveals the email sign-in form; a failed request shows an error with retry instead. Startup retries a network failure, timeout, HTTP 408, or server error once after 500 ms. Each read includes the response body, with a 10-second attempt limit and 20-second overall deadline. Other HTTP failures and malformed responses do not retry. Exhaustion exposes Try again; valid signed-out responses never retry. Failed attempts send a best-effort anonymous diagnostic report, including whether the second attempt recovered. Late responses from timed-out or unmounted attempts cannot change the session or overwrite a retry. The static HTML shows “Starting slowmass…” before the application runs; React shows “Loading slowmass…” while bootstrap waits. A separate small `public/startup.js` script offers Reload after fifteen seconds if the main bundle never starts. The entry point signals successful startup and cancels that guard. This recovery script must itself load and cannot recover a suspended browser or a fully blocked network. It stores no private data and makes no API calls. Missing credentials show an availability message; network and link errors are distinct. Addresses without an account stay on the form with instructions to ask a member to text them an event link. Only eligible requests advance to the email-link instructions.

The resolved profile is passed to the member application without another startup read. Feed data begins immediately afterward, reducing startup from four sequential API requests to two. Signed-in members see the member application; sign-out is available under Settings. The header uses the locally hosted text wordmark, and signed-out members see a bounded email sign-in form. Magic-link sign-in handles returning members; new members join only through an event link and then give a name.

After requesting a link, focus/visibility return events recheck the current session, without polling. A manual check button gives an explicit status if that window still has no session. This cannot transfer a session between isolated browsers.

Installed apps may have a separate session from the browser opened by an email link. Only standalone windows show the collapsed `PasteLoginLink` helper, letting the member copy an unused link from email and consume it inside the app. Regular browser login has no pasted-link form. The input is masked and never logged or persisted. Validation accepts only the current origin's exact Better Auth verification path, rejects credentials/duplicate or missing tokens, and reconstructs the URL with fixed local success/error callbacks. Better Auth remains responsible for expiry, single use, membership eligibility, and session cookies. No new token issuer, session-transfer endpoint, or auth bypass is introduced. Copying an already-used link requires requesting a new one.

When a member API rejects an expired or revoked session, Welcome clears the mounted member screens and shows email sign-in with an explanation. It does not leave users retrying an unauthorized screen. The session subscription uses a layout effect so it is active before child request effects; it is scoped by member identity and cleaned up on sign-out/unmount. Temporary network/server failures do not sign the member out.

The initial HTML shell and bootstrap loading/error states share a compact 26px wordmark at all viewport sizes. The header link retains its existing 48px touch target. This affects the in-app loading header, not platform-generated icon splash screens.

Welcome passes bootstrap's pending device setup and push-subscription flags to the member shell; missing fields from an earlier Worker mean no suggestion. Sign-in resumes incomplete profile/photo setup or opens the requested member page directly when the profile is complete. Installed-app session reuse and the unused-link helper are unchanged.

An event's URL (`/#event/<link>`) is the only invitation. Signed in, the member app opens it. Signed out, Welcome checks only whether the link works—the credential goes in a POST body and the reply holds just the event ID and whether it admits new people—then asks for an email under “You're invited to an event”, revealing nothing else. The sign-in email carries the link as metadata and returns to `#event/<id>`, where new members first give a name. Closed events tell new people to ask the host while members can still sign in; a link that no longer works falls back to normal sign-in. `?error=event` explains a failed event sign-in. The credential stays in the fragment and component memory.
