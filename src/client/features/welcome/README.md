# Welcome

Shows a neutral loading state until service availability, session, and the current member's profile are known from one private `/api/bootstrap` response. Only a confirmed signed-out response reveals the email sign-in form; a failed request shows an error with retry instead. Startup retries a network failure, timeout, HTTP 408, or server error once after 500 ms. Each read includes the response body, with a 10-second attempt limit and 20-second overall deadline. Other HTTP failures and malformed responses do not retry. Exhaustion exposes Try again; valid signed-out responses never retry. Failed attempts send a best-effort anonymous diagnostic report, including whether the second attempt recovered. Late responses from timed-out or unmounted attempts cannot change the session or overwrite a retry. The static HTML shows “Starting slowmass…” before the application runs; React shows “Loading slowmass…” while bootstrap waits. A separate small `public/startup.js` script offers Reload after fifteen seconds if the main bundle never starts. The entry point signals successful startup and cancels that guard. This recovery script must itself load and cannot recover a suspended browser or a fully blocked network. It stores no private data and makes no API calls. Missing credentials show an availability message; network and link errors are distinct. Ineligible addresses stay on the form with instructions to ask a slowmass member to invite that email address. Only eligible requests advance to the email-link instructions.

The resolved profile is passed to the member application without another startup read. Feed data begins immediately afterward, reducing startup from four sequential API requests to two. Signed-in members see the member application; sign-out is available under Settings. The header uses the locally hosted text wordmark, and signed-out members see a bounded email sign-in form. Magic-link sign-in handles returning members and remains a fallback for invited new members, followed by profile setup when needed.

New invitation emails open `/join` with a secret in the URL fragment. `JoinInvitation` shows a loading state, then the inviter, invited email, expiry, and mutual-follow disclosure. Rendering or previewing never accepts the invitation. Only the Accept invitation button makes the acceptance POST; success opens the app with the library-issued session and existing onboarding. A different signed-in account requires explicit sign-out. Cancelled, expired, malformed, and used links have distinct explanations and a normal sign-in path. Network failures preserve retry and recovery options. The credential is held in component memory and the incoming fragment only, never local/session storage, rendered inputs, analytics, or query strings. Opening the page does not send another email.

After requesting a link, focus/visibility return events recheck the current session, without polling. A manual check button gives an explicit status if that window still has no session. This cannot transfer a session between isolated browsers.

Installed apps may have a separate session from the browser opened by an email link. Only standalone windows show the collapsed `PasteLoginLink` helper, letting the member copy an unused link from email and consume it inside the app. Regular browser login has no pasted-link form. The input is masked and never logged or persisted. Validation accepts only the current origin's exact Better Auth verification path, rejects credentials/duplicate or missing tokens, and reconstructs the URL with fixed local success/error callbacks. Better Auth remains responsible for expiry, single use, membership eligibility, and session cookies. No new token issuer, session-transfer endpoint, or auth bypass is introduced. Copying an already-used link requires requesting a new one.

When a member API rejects an expired or revoked session, Welcome clears the mounted member screens and shows email sign-in with an explanation. It does not leave users retrying an unauthorized screen. The session subscription uses a layout effect so it is active before child request effects; it is scoped by member identity and cleaned up on sign-out/unmount. Temporary network/server failures do not sign the member out.

The initial HTML shell, bootstrap loading/error states, and invitation-loading screen share a compact 26px wordmark at all viewport sizes. The header link retains its existing 48px touch target. This affects the in-app loading header, not platform-generated icon splash screens.

`/invite#…` is the shared-link landing page, separate from personal `/join#…` credentials. Preview is bounded and does not authenticate or create membership. It discloses the inviter and optional following, then sends a one-time email verification link. The shared credential remains in the fragment/component state and POST body only; no local storage, query-string transfer, analytics, or credential-bearing logs. Verification returns to normal profile setup and rechecks the exact current credential. Expired, replaced, revoked, or inactive-inviter links offer a new invitation/sign-in path. Existing signed-in visitors open their account. The installed-app pasted email-link helper remains available after sending.

Bootstrap also carries optional device-setup progress. After authenticating, Welcome passes it to member screens so a newly installed app resumes setup without repeating a completed profile. Missing progress from an older Worker response defaults to no offer during rollout. Authentication and the unused-link helper are unchanged.
