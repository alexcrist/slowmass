# Welcome

Shows a neutral loading state until service availability, session, and the current member's profile are known from one private `/api/bootstrap` response. Only a confirmed signed-out response reveals the email sign-in form; a failed request shows an error with retry instead. Startup retries a network failure, timeout, HTTP 408, or server error once after 500 ms. Each read includes the response body, with a 10-second attempt limit and 20-second overall deadline. Other HTTP failures and malformed responses do not retry. Exhaustion exposes Try again; valid signed-out responses never retry. Failed attempts send a best-effort anonymous diagnostic report, including whether the second attempt recovered. Late responses from timed-out or unmounted attempts cannot change the session or overwrite a retry. The static HTML shows “Starting slowmass…” before the application runs; React shows “Loading slowmass…” while bootstrap waits. A separate small `public/startup.js` script offers Reload after fifteen seconds if the main bundle never starts. The entry point signals successful startup and cancels that guard. This recovery script must itself load and cannot recover a suspended browser or a fully blocked network. It stores no private data and makes no API calls. Missing credentials show an availability message; network and link errors are distinct. Addresses without an account stay on the form with instructions to ask a member to text them an invite link. Only eligible requests advance to the email-link instructions.

The resolved profile is passed to the member application without another startup read. Feed data begins immediately afterward, reducing startup from four sequential API requests to two. Signed-in members see the member application; sign-out is available under Settings. The header uses the locally hosted text wordmark, and signed-out members see a bounded email sign-in form. Magic-link sign-in handles returning members; new members join through an invite or event link and then give a name.

After requesting a link, the shared confirmation leads with “Open the sign-in link in your email.” and gives the address, spam-folder reminder, and ten-minute single-use limit. Email-entry instructions disappear, and focus moves to the confirmation heading. Focus, visibility return, restored-page, and reconnect events recheck the current session without polling or a routine confirmation button. Simultaneous events share one read; hidden windows do not start checks. Checks reuse startup's response validation, deadlines, and transient retry. A confirmed signed-out result keeps the email instructions; an exhausted failure shows Try again. Unmount/sign-in aborts checks and removes listeners, and late responses cannot replace the current state. This cannot transfer a session between isolated browsers.

Installed apps may have a separate session from the browser opened by an email link. Only standalone windows show the collapsed “Trouble signing in?” disclosure, letting the member copy an unused link from email and consume it inside the app. After requesting an email, the same disclosure offers Send a new link to the same address, retaining the original invite/event metadata and callback. Pending resends suppress duplicate requests; failures keep the confirmation and helper usable, and server eligibility/rate limits still apply. Regular browser login has no pasted-link form or resend action. The input is masked and never logged or persisted. Validation accepts only the current origin's exact Better Auth verification path, rejects credentials/duplicate or missing tokens, and reconstructs the URL with fixed local success/error callbacks. Better Auth remains responsible for expiry, single use, membership eligibility, and session cookies. No new token issuer, session-transfer endpoint, or auth bypass is introduced. Copying an already-used link requires requesting a new one.

When a member API rejects an expired or revoked session, Welcome clears the mounted member screens and shows email sign-in with an explanation. It does not leave users retrying an unauthorized screen. The session subscription uses a layout effect so it is active before child request effects; it is scoped by member identity and cleaned up on sign-out/unmount. Temporary network/server failures do not sign the member out.

The initial HTML shell and bootstrap loading/error states share a compact 26px wordmark at all viewport sizes. The header link retains its existing 48px touch target. This affects the in-app loading header, not platform-generated icon splash screens.

Welcome passes bootstrap's pending device setup and push-subscription flags to the member shell; missing fields from an earlier Worker mean no suggestion. Sign-in resumes incomplete profile/photo setup or opens the requested member page directly when the profile is complete. Installed-app session reuse and the unused-link helper are unchanged.

An invite link (`/#invite/<link>`) invites someone to slowmass. Signed out, Welcome posts the credential to `/api/invite-link/check`, whose reply says only whether the link admits new people, then asks for an email under “You’re invited to slowmass”. The sign-in email carries the link as metadata and returns to `/`, where new members give a name and then add a profile photo. A link that no longer works says so and falls back to normal sign-in, and a failed join through one returns with `?error=invite`. A signed-in member opening an invite link just sees the app: Welcome drops the credential from the address before member routes read it.

An event's URL (`/#event/<link>`) also invites people. Signed in, the member app opens it. Signed out, Welcome fetches a limited title/date/cover preview through the events feature, then asks for an email to see details and RSVP. The credential goes only in POST bodies; the cover uses a transient blob URL with loading/error/retry states and is discarded on unmount. Description, exact time, location, and member information require sign-in. The sign-in email carries the link as metadata and returns to `#event/<id>`, where new members first give a name. Closed events tell new people to ask the host while members can still sign in; a link that no longer works falls back to normal sign-in. `?error=event` explains a failed event sign-in. The credential stays in the fragment and component memory.

Regular, invite-link, and event-link email forms share one joined email/submit control: a labeled email input with a green paper-plane button on its right. The icon button retains an accessible action name, keyboard submission, disabled sending state, and an announced pending status. The installed-app unused-link helper uses the same treatment. Account-creation and password reassurance sentences are omitted; eligibility and delivery errors remain explicit.

The confirmation has no account-switch action. Same-email resend is available only inside installed-app recovery. Name onboarding likewise has no account-switch control; Settings retains normal sign-out.
