# Events

The Events tab lists upcoming events (soonest first) and past events (most recent first) that the member hosts, answered, or opened through the current link (“You’re invited”), with explicit page controls. Event rows lead their date, optional location, and attendance status with decorative calendar, pin, and person icons. Date and location icons are shared with the event detail page. Rows use matching text size and line height with one consistent gap between the bold title, date, optional location, and answer. Members with a profile photo can create events from New event, at the right end of the Upcoming/Past tab row; the form reuses the post crop editor for a required cover photo, collects a title, date, start time, optional end time, location, and description, and uses the browser’s time zone. An end time earlier than the start ends the next day. Editing shows the existing authorized cover photo until a cropped replacement preview is ready, keeps the event’s time zone, and shows no notification warning; detail edits are silent. Stable event, notification/message, and upload IDs make unchanged retries converge; changing a message starts a new attempt.

`EventRoute` opens `#event/<link>` URLs through `/api/events/open` (explaining an unavailable link) and shows `#event/<id>` routes directly; the page then rewrites the address bar to the event’s one URL so copying it works. Event pages have no back control: Events is always in the sidebar or bottom bar. The cover is a keyboard-accessible button that opens the shared large-photo modal on phones and desktop, using the same authorized cover URL; closing or navigating away discards the modal. Pages show the cover photo (full width, above the details; from 1100px, a sticky right column beside them, scaled to fit the viewport height), title, date and time in the event’s time zone with its abbreviation (`time.ts`), location, an Add to calendar button, hosts with an outline crown, and description. Date, time, and location have decorative outline icons. The details use one consistent vertical gap through the answer buttons, and the Guests heading sits 4px above its tabs. Hosts and guests answer with three toggle buttons, each with an owner-chosen emoji (🪩 Going, 🎲 Maybe, 🫠 Can’t go, hidden from assistive technology); the choice gets a heavier border and gray fill. A saved answer fills the row while the other options collapse and fade. Selecting it again reveals or hides the alternatives without changing the answer or making a request. Only a confirmed different answer collapses the options again; failed saves keep them open with the previous answer selected. Hidden options leave the keyboard and accessibility order, and reduced-motion preferences disable the transitions. Until guests answer, an explicit locked Guests section says “RSVP to see who’s going” and explains that any answer unlocks guests and activity; closed events explain that the list remains hidden and RSVPs are closed. Beside the title, only hosts (the creator and accepted co-hosts) see the mail icon that opens a dialog with the event URL, a Copy button, and “Send the link to your friends to invite them.”; when copying fails, the dialog says to select the link instead. The description has equal space between the title and copy row, accounting for the close button’s taller touch target. Hosts also get an overflow menu with Edit event, Edit hosts, Send notification, and Cancel event; cancelling asks for confirmation. Creators also get Delete event, including on cancelled and past events. On a cancelled event the creator’s overflow menu contains only Delete event. Its confirmation explains that deletion removes the event for everyone, disables its link, sends no notification, and cannot be undone. Submission blocks duplicate clicks and dismissal, preserves failures for retry, and returns to Events only after success. Leaving aborts the pending request and prevents a late redirect. Edit hosts lists hosts (the creator can’t be removed; other hosts can be removed or stop hosting, which returns them to Events) and pending emails, and adds a host by email. Adding replies the same whether or not the email has an account. A member whose email a host added sees a prompt on the event to become a host or decline. After answering, the guest list uses keyboard-navigable tabs per answer with counts, and the activity log combines answers and messages, newest first, with a message composer below it matching comments and no extra top margin. Removing a message asks for confirmation. Guest lists and the log identify people by name only, since event joining only asks for a name. Guests without a profile photo show their initial and have no profile link. Host, guest-list, activity, and host-dialog avatars link to available profiles with accessible names and expanded pointer targets. Event-only viewers reach the profile preview directly; Request to follow opens account setup, and saving a photo returns to that profile. Host-dialog links are unavailable during a pending mutation. Guest names with a profile photo also link to the profile for event-only viewers.

Send notification opens the shared dialog with a required message and explains that everyone who RSVP’d and the other hosts receive Activity, only opted-in devices receive push alerts, and no email is sent. Cancel and Send notification share one action row, including on phones. The native form has a 2,000-character limit, blocks duplicate submission and dismissal while sending, and preserves its text and ID after failure. Editing the text starts a new attempt. Success closes the dialog, announces confirmation, and refreshes the event log without discarding an ordinary message draft. Only hosts of an uncancelled event see the action; the server independently enforces access. Detail edits produce no log entries or notifications, including historical change entries.

Members without a profile photo use Events, Activity, Settings, Find, and other members’ profile previews within the full navigation; Feed, New post, and their own unfinished Profile have no lock badges and explain the account-setup requirement, then Continue opens username and profile-photo selection on one screen with Finish. Signed-out visitors see `EventPreview`: a clear processed cover, title, and date followed by the [email form](../welcome/README.md). Its cover fetch keeps the credential in a POST body and revokes its in-memory blob URL on retry/unmount; failures leave the email form usable. No description, location, exact time, hosts, or guests enter the preview. Create/edit forms explain which fields anyone with the link can preview.

Cover uploads now distinguish saving details, byte transfer, and processing/saving, with measured transfer percentages and slow-phase messages. Details requests have a 30-second deadline; cover uploads have a two-minute deadline. Unmount aborts pending requests and suppresses late navigation; a synchronous request guard prevents duplicate submissions. Unchanged retries preserve IDs and photo bytes. Changing a new event's details or saved appearance rotates both its event ID and its cover-upload ID, so a prior cover acknowledgement cannot be mistaken for publication of the new draft. As before, editing after an uncertain result can start a separate event; retry unchanged details first or check Events.

## Calendar copies

Signed-in viewers, including event-only members before RSVP, see a compact Add to calendar button below location (or time if location is absent) and above the host row. Its decorative outline calendar-plus icon is distinct from the date’s calendar grid. The host row has one decorative outline crown before the avatars/names and can wrap on narrow screens. The shared native dialog contains only its title, close control, and equally weighted Google Calendar, Apple Calendar, and Outlook choices with local, monochrome provider icons beside their labels. It preserves normal keyboard/close/focus behavior and event appearance. Cancelled events omit the action; signed-out previews never show it.

Google and Outlook open prefilled calendar entries with no opener/referrer; their links request a new tab, and the device may hand them to an installed calendar app. Google uses the template entry point to avoid the mobile direct-editor handoff that can open an empty calendar. Apple opens the session-authorized calendar download, for importing into Calendar. No provider is contacted just by opening the dialog. These are one-time copies; an event without an end uses one hour. Copies use the event’s actual UTC instants and contain only its details and an ID-based, access-controlled link back to slowmass; the invitation credential is excluded. Nothing is added to a calendar until the member completes the provider/import flow. The [shared formatting module](../../../shared/event-calendar/README.md) owns encoding and file format rules. Provider UI and native-device import behavior remain unverified; local tests cover link parameters, placement, dialog dismissal, and server authorization.

## Appearance

Create and Edit event use the same `EventForm` and `EventAppearanceDialog`, offering a rainbow-filled Color theme button with dark lettering and a Fonts button in the existing handwritten Caveat face. Each opens a native radio-group dialog with a live preview and explicit Save/Cancel, without introductory helper text. Font options show only the choice name in its display face, without a subtitle or separate wordmark sample. Opening Fonts loads those local previews on demand; Color theme does not load the catalog. Cancel, Escape, and backdrop dismissal restore the last saved appearance. For existing events, saving disables dismissal and duplicate submissions, and a confirmed response updates the page immediately. Failures preserve the selection for retry; Reload appearance reads the latest authorized choices and updates the concurrency guard without losing unfinished event details. Unmount aborts pending saves/reads and ignores late replies. For existing events, appearance saves separately from the event-detail form. For new events, dialog saves keep choices locally until Create event submits them with the initial draft; opening, previewing, saving, or cancelling those dialogs makes no API request. Cancelling restores the last confirmed selection in the form. An unchanged creation retry preserves its appearance and upload identity.

The mounted event page, create/edit form, or credential-authorized signed-out preview owns document-root color and heading-font variables. Colors cover navigation/header portals, safe areas, native dialogs, body text, headings, the wordmark, and controls; fonts apply only to headings, so the sidebar and phone-header logo and navigation labels keep the app’s own faces. A layout-effect cleanup restores previous values and the browser theme color on route changes, unavailable events, or unmount. Event lists, profiles, Activity, and Settings use normal app styling. The default Original pairing keeps Source Sans 3 headings; other pairings use their display face for headings. Original, Handwritten, and Classic remain available alongside Bungee Shade, Monoton, Fascinate Inline, and Rubik Wet Paint. The four party faces use their native 400 weight; all choices use Source Sans 3 for body text. Unsupported characters fall back to system fonts. No appearance or private event data is stored in browser storage.

[Shared identifiers](../../../shared/event-appearance/README.md) keep client/server choices aligned. The palette distinguishes the page canvas, input surface, structural dividers, stronger control outlines, and hover/disabled surfaces. These roles replace the normal gray boundaries throughout the shell, including navigation, forms, file controls, and upload progress. Crop handles stay high contrast against photo bytes. Local WOFF2 face declarations use swap and are requested only when used by the active pairing or visible font previews; no catalog preloads, third-party font requests, or new runtime dependencies are introduced. Font files have content-hashed names and immutable caching; licenses and source URLs live in `public/fonts/events/`. Contrast calculations, font-asset checks, component lifecycle tests, and Workers/D1 tests verify the contract without browser or visual testing.
