# Member screens

Mobile profile tabs have a 16px side inset on both own and accepted-follow profiles, while the photo grid stays edge to edge. The inset applies through the loading/authorization wrapper around the tabs.

On phones, five bottom-bar destinations (Feed, Find, New post, Events, Profile) organize the app, and Activity with its unread badge sits at the right of the wordmark header on every page. The desktop sidebar lists all six (adding Activity), so the header is hidden there. The shell renders those header controls into a slot Welcome provides. Member pages omit visible page-title labels and their reserved space, retaining visually hidden headings for screen readers. Onboarding keeps its instructional headings. Hash links support own and other member profiles and back/forward navigation. Each route has a distinct keyed page root so edit forms and list state cannot accumulate across pages. A Node component regression test repeatedly switches pages; no browser or visual testing is used.

`MemberNavigation` owns the shared destination links. CSS presents a desktop icon sidebar with labels revealed on hover/focus and a mobile bottom bar with persistent labels. Selecting the active Feed, Events, Activity, or own Profile link remounts just that page and starts a fresh read from the first page; the member session stays mounted. New post and Find are not reset on reselection, and modified clicks keep their normal behavior. Links always have explicit accessible names; the profile icon uses the member’s photo when available, otherwise an outline person icon. Your profile has a mail icon and a Settings gear beside the avatar/name group, aligned to the top of the header row. The mail icon opens the [invite link](../invite-links/README.md) dialog; there is no invitations page, and other profiles never show it. Settings is accessed through that gear and a bottom desktop-sidebar link; mobile navigation retains its five destinations. The sidebar logo anchors its initial letter while revealing the full wordmark, with reduced-motion support. The member shell uses the notifications feature’s unread-count hook for the Activity bubble, after onboarding is complete, plus one while the device-setup suggestion has an unseen step on this device. It refreshes the count without reloading the current screen; read acknowledgements and follow decisions refresh it immediately. The link keeps its accessible Activity name and describes the unread total. The avatar still loads through the authenticated media endpoint.

Completed profiles always display their saved photo; letter placeholders and optional-photo rendering have been removed. Profiles contain identity information, follow controls for other members, and a paginated photo grid when permitted. Your own profile and accepted-follow profiles use Posts, Following, and Followers tabs; the selected tab is represented in the hash without remounting the identity header. Only the selected panel fetches data. Post-grid pagination cursors survive a visit to a focused post; returning refetches authorized content. Connection tabs start at their first page when entered. Settings holds editing, blocked accounts, Invite to slowmass (opening the shared invite-link dialog), installation, a full-app reload, sign-out, and collapsed account deletion in matching rows. Follow requests are handled inside Activity. Secondary pages have labeled back links above their content; Settings omits its profile link on desktop. Dedicated post pages and other members’ profiles show a back link to the prior in-app route (including a profile tab), with Feed as the direct-link fallback. Your own profile has no back link. Legacy standalone Following/Followers URLs remain valid. New members first see only a name field (no username; the server generates one) with one contextual introduction and no duplicate name help or account-switch action. Saving it keeps people on the event route that brought them; anyone else goes on to choose a username and add a profile photo, which they can leave for later. Members without a photo then use the events-only app described below; photo features unlock when they add one from Settings or a photo-only navigation destination. Saved names survive upload failures and reloads. Account deletion lives in Settings. Edit profile allows username changes; successful saves update the profile route and main navigation, while conflicts retain the draft. The old username becomes available to others; old profile links do not redirect.

Find supports fuzzy matching through the API with a 350 ms debounce and three-character minimum. Clear the field to browse the directory; each search/browse starts with a random seed retained across its pages. There is no manual shuffle control. All lists use explicit page controls. Private fields are displayed only when supplied by the authorized API.

The initial own profile loads once per member screen mount; navigation and onboarding wait until that read succeeds. Avatar changes update that parent state; profile pages fetch current details. Follow requests and cancellations revalidate in place with controls disabled, preserving the identity header and avatar without starting another post-grid read. Connection removals discard the confirmed removed row immediately and retain other rows during revalidation. Unfollowing from a profile still clears private content before reloading; blocking navigates away. Failed revalidation clears retained results and offers Retry. Read retries clear old errors immediately; pending or failed reads never imply an empty list or a private profile. Errors retain inputs and allow retry, and unmounting cancels pending reads. No private data is placed in local storage or a persistent client cache.

Following/follower rows show an avatar and username. Other members’ lists use a profile-scoped API and link to each account without management actions; own lists retain compact actions. Pending and non-followers cannot open relationship tabs. Each tab fetches only its selected list with explicit pagination and retry states. Removal and unfollowing require a modal confirmation; failures retain it for retry, and only success refreshes the list. Blocked accounts omit avatars because their media is not accessible. Other profiles put Unfollow (for accepted follows) and Block account in the shared overflow menu. Request to follow and Cancel request remain compact inline controls with equal spacing above and below them. Both profile unfollowing and blocking open a confirmation naming the account. Cancellation sends no mutation; pending actions disable dismissal and resubmission, and failures remain in the dialog for retry. Successful blocking returns to Find; successful unfollowing reloads the authorized profile. Follow requests and cancellation of pending requests remain immediate.

Settings composes the separate push feature's explicit per-device opt-in and disable control, alongside existing installation and account controls.

On a profile’s Posts tab, the bounded post-page request starts alongside the profile request. Posts and images are not rendered until the profile response grants content access. Denial, errors, or navigation discard the panel and cancel its request; late responses cannot reveal old content. This can add one denied post request when visiting an unfollowed profile. Following/Followers tabs still wait for profile authorization. No persistent client cache is introduced.

Pressing Finish in account setup saves the username and photo, then opens the selected photo-app destination; setup from Settings opens Feed. There is no final installation/notification onboarding page, including for accounts with legacy pending setup. Settings retains installation and per-device notification controls.

Members without a profile photo can use Events, event pages, Activity, Settings, Find, and other members’ profile previews. Previews show the existing identity header, avatar, Request to follow control, and private-account message; they never prefetch posts or show bios, connection tabs, or relationship management. Request to follow opens the existing setup flow at the profile’s join route. Finish returns to that profile without sending a follow request. They see the same phone bottom bar and desktop sidebar as other members; gated destinations (Feed, New post, and the member’s own unfinished Profile) remain tappable without lock badges and include an accessible setup explanation. Selecting one renders `ProfileSetup` without mounting or fetching the private feature. The prompt explains that using the rest of slowmass requires a username and profile photo, with primary Continue and secondary Back to event buttons (Back to events when no event is in bounded route history). Continue opens one screen with a photo picker, editable username, and Finish at the bottom. Settings → Set up profile and non-event onboarding open that screen directly. The username field is shared with Edit profile.

Cropping prepares the photo in memory without saving or granting access. Finish first validates/saves the username through the existing profile API, then uploads the photo with a stable operation ID. Username conflicts keep both drafts in place without uploading. A failed photo save keeps the chosen username on the server and both fields in the current form; retries reuse the same photo bytes and ID. Changes to the photo create a new operation. Submission and photo changes are disabled while saving; duplicate submissions are ignored, username saves time out after 30 seconds, and uploads retain the shared two-minute deadline. Navigation aborts pending work and ignores late replies, but cannot undo a server commit. Reloading uses server state and discards unsaved photo bytes. Only confirmed photo success opens the selected destination, updating an own-profile URL together with the member state so the released username is never fetched; other members' destinations stay unchanged.

Mobile Activity and Settings stay in the header. Event pages have no back control, since Events is always in the navigation. Settings offers Set up profile, Edit name (only the name field; the username and bio are saved unchanged), installation, notifications, sign out, and account deletion.
