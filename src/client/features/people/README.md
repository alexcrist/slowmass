# Member screens

Mobile profile tabs have a 16px side inset on both own and accepted-follow profiles, while the photo grid stays edge to edge. The inset applies through the loading/authorization wrapper around the tabs.

Five primary destinations (Feed, Find, New post, Activity, Profile) organize the app. Member pages omit visible page-title labels and their reserved space, retaining visually hidden headings for screen readers. Onboarding keeps its instructional headings. Hash links support own and other member profiles and back/forward navigation. Each route has a distinct keyed page root so edit forms and list state cannot accumulate across pages. A Node component regression test repeatedly switches pages; no browser or visual testing is used.

`MemberNavigation` owns the shared destination links. CSS presents a desktop icon sidebar with labels revealed on hover/focus and a mobile bottom bar with persistent labels. Selecting the active Feed, Activity, or own Profile link remounts just that page and starts a fresh read from the first page; the member session stays mounted. New post and Find are not reset on reselection, and modified clicks keep their normal behavior. Links always have explicit accessible names; the profile icon always uses the member's profile photo. Your profile has an Invite friends shortcut immediately before the Settings gear beside the avatar/name group, with both groups aligned to the top of the same header row; invitations opened there return to your profile. Settings is accessed through that gear and a bottom desktop-sidebar link; mobile navigation retains its five destinations. The sidebar logo anchors its initial letter while revealing the full wordmark, with reduced-motion support. The member shell uses the notifications feature’s unread-count hook for the Activity bubble, after onboarding is complete, plus one while the device-setup suggestion has an unseen step on this device. It refreshes the count without reloading the current screen; read acknowledgements and follow decisions refresh it immediately. The link keeps its accessible Activity name and describes the unread total. The avatar still loads through the authenticated media endpoint.

Completed profiles always display their saved photo; letter placeholders and optional-photo rendering have been removed. Profiles contain identity information, follow controls for other members, and a paginated photo grid when permitted. Your own profile and accepted-follow profiles use Posts, Following, and Followers tabs; the selected tab is represented in the hash without remounting the identity header. Only the selected panel fetches data. Post-grid pagination cursors survive a visit to a focused post; returning refetches authorized content. Connection tabs start at their first page when entered. Settings holds editing, invitations, blocked accounts, installation, a full-app reload, sign-out, and collapsed account deletion in matching rows. Follow requests are handled inside Activity. Secondary pages have labeled back links above their content; Settings omits its profile link on desktop. Dedicated post pages and other members’ profiles show a back link to the prior in-app route (including a profile tab), with Feed as the direct-link fallback. Your own profile has no back link. Legacy standalone Following/Followers URLs remain valid. New members see profile setup followed by a required photo step. Mutual follows are disclosed on personal invitation acceptance; shared links create no automatic follows, so generic onboarding makes no promise of them. Navigation and member features remain unavailable until the photo is saved. Unfinished onboarding resumes this step on sign-in. Completed profile data survives upload failures and reloads. Onboarding uses a narrow form, a clearly spaced photo action and helper text, and a quiet Use a different account action on both steps. Account deletion lives in Settings. Edit profile allows username changes; successful saves update the profile route and main navigation, while conflicts retain the draft. The old username becomes available to others; old profile links do not redirect.

Find supports fuzzy matching through the API with a 350 ms debounce and three-character minimum. Clear the field to browse the directory; each search/browse starts with a random seed retained across its pages. There is no manual shuffle control. All lists use explicit page controls. Private fields are displayed only when supplied by the authorized API.

The initial own profile loads once per member screen mount; navigation and onboarding wait until that read succeeds. Avatar changes update that parent state; profile pages fetch current details. Follow requests and cancellations revalidate in place with controls disabled, preserving the identity header and avatar without starting another post-grid read. Connection removals discard the confirmed removed row immediately and retain other rows during revalidation. Unfollowing from a profile still clears private content before reloading; blocking navigates away. Failed revalidation clears retained results and offers Retry. Read retries clear old errors immediately; pending or failed reads never imply an empty list or a private profile. Errors retain inputs and allow retry, and unmounting cancels pending reads. No private data is placed in local storage or a persistent client cache.

Following/follower rows show an avatar and username. Other members’ lists use a profile-scoped API and link to each account without management actions; own lists retain compact actions. Pending and non-followers cannot open relationship tabs. Each tab fetches only its selected list with explicit pagination and retry states. Removal and unfollowing require a modal confirmation; failures retain it for retry, and only success refreshes the list. Blocked accounts omit avatars because their media is not accessible. Other profiles put Unfollow (for accepted follows) and Block account in the shared overflow menu. Request to follow and Cancel request remain compact inline controls with equal spacing above and below them. Both profile unfollowing and blocking open a confirmation naming the account. Cancellation sends no mutation; pending actions disable dismissal and resubmission, and failures remain in the dialog for retry. Successful blocking returns to Find; successful unfollowing reloads the authorized profile. Follow requests and cancellation of pending requests remain immediate.

Settings composes the separate push feature's explicit per-device opt-in and disable control, alongside existing installation and account controls.

On a profile’s Posts tab, the bounded post-page request starts alongside the profile request. Posts and images are not rendered until the profile response grants content access. Denial, errors, or navigation discard the panel and cancel its request; late responses cannot reveal old content. This can add one denied post request when visiting an unfollowed profile. Following/Followers tabs still wait for profile authorization. No persistent client cache is introduced.

After the required photo is saved, members enter the requested app page directly. There is no final installation/notification onboarding page, including for accounts with legacy pending setup. Settings retains installation and per-device notification controls.
