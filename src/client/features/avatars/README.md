# Profile photo and cropping

Account setup combines a required profile photo and username on one screen, saved with Finish. Interrupted setup resumes from the server’s saved profile state. Completed profiles always have a photo; there is no optional-avatar mode. Settings → Edit profile uses the same crop dialog (`AvatarCropDialog`) from the avatar in its header to replace a photo; removal is unavailable. Both parents upload through `uploadAvatar`. Successful uploads update the parent profile state and navigation avatar. Profile photos are treated as public identity information; setup and editing make no promise of a restricted audience.

Choose profile photo / Change photo opens the file picker and immediately opens a native modal crop editor. In account setup, Use photo prepares a draft and circular preview without uploading; the parent setup form saves it on Finish. Cancelling a replacement keeps the selected draft, and replacing it or leaving releases its object URL. In Edit profile, Use photo prepares the same kind of draft, previewed in the header, and Save uploads it after the profile details. Cancel/Escape discards an unsubmitted selection without network activity; while the crop is being prepared, duplicate confirmations, gestures, and dismissal are blocked. The modal traps focus natively and restores focus to its trigger when closed.

JPEG, PNG, and WebP originals are limited to 32 MiB and 40 megapixels; the locally encoded upload remains limited to 8 MiB. The browser respects image orientation, previews a square crop inside a circular mask, and supports one-finger dragging, two-finger pinch zoom and repositioning, arrow keys, and the zoom slider. Pinching anchors the photo beneath the gesture midpoint, stays within the existing 1–4× range and image bounds, and resumes dragging when one finger lifts. Cancellation or lost capture removes only that pointer; extra fingers are ignored. Fractional gesture coordinates avoid accumulated rounding drift; preview and upload still share the same bounded raster crop. The chosen crop is encoded at up to 1600px before upload, without upscaling small crops; the server still validates and re-encodes all submitted bytes. Client validation is only for usability. Decoded bitmaps are released on replacement/unmount, and obsolete decoding results are ignored.

A prepared crop and idempotency key are retained together after a network failure, so retrying cannot upload a different image under the same key. The setup form retains this same prepared payload through username conflicts and upload failures. Adjusting the crop or selecting another file starts a new operation. Confirmed server processing failures require a new attempt and count toward quotas. Unmounting aborts pending work; onboarding advances only after the server confirms success. Current photos remain intact until a replacement succeeds.

Original files and previews stay in memory. Saved photos are fetched through the authorized private media route; there is no persistent client cache, public URL, or third-party image host.

On profile pages, the photo opens an image-only native modal, with no white frame or visible heading. A labeled close icon sits at the viewport’s top right, outside the image. The viewer has loading, failure, and retry states and requests the large variant only after opening. Closing or navigating away discards the viewer; opening it again loads through the same private media route. This works for your own profile and other visible member profiles, including before a follow is accepted. Avatars elsewhere still link to profiles. Small avatars elsewhere still use the 320px version. Existing photos retain their current quality; new uploads store both sizes.

Saving now distinguishes local crop preparation, photo transfer with a measured percentage, and server processing/saving. Slow-phase messages appear after 15 seconds. Local preparation is bounded to 30 seconds; the upload response is bounded to two minutes. A timed-out or disconnected save releases the form and offers Retry save with the same prepared bytes and operation ID. The current photo/onboarding state changes only after confirmed success. A server-declared failed attempt requires choosing the photo again; failed attempts count toward the allowance.
