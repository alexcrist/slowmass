# Notifications

Every Activity image uses the same fixed 64px square footprint, including on narrow phones. Profile avatars are circular and post thumbnails are square; shared sizing prevents notification types from drifting apart.

Requests, new followers, grouped likes, and comments share one newest-first timeline with explicit Newer/Older pagination. Consecutive likes on a post form one row; other activity in between splits them, and the newer row says “N more people like your photo.” when the server marks it `more`. There are no filters or separate request section. Like/comment rows are native post links with private, lazily loaded 64px thumbnails on the left; the entire padded row is clickable and keyboard accessible. Targets reauthorize through the existing post/media APIs. Follow requests and new-follower rows link their private circular avatar and summary to the current profile. Their independent actions sit at the right, vertically centered; Accept uses the primary green style. Summary text wraps on narrow phones while actions remain inline. New-follower rows use “started following you” and offer Follow back only when the server reports no outgoing pending or accepted follow and no dismissal. Follow back sends the normal private follow request. The labeled dismiss control saves across devices, hides only this event’s prompt, and leaves the notification and read state intact. Failures retain actions for retry; successful mutations revalidate current eligibility while retaining unaffected rows and images. Confirmed decisions remove the resolved request immediately; following back or dismissing hides only that prompt. They share the same summary visibility tracking and badge as every other activity type. Reading a request does not accept, deny, or hide it. Acceptance replaces it with follower activity; removed sources disappear through normal authorized reads.

The member navigation shows one unread-item count in a Douglas Fir green badge with white text, capped visually at 99+. A like group counts as one item. Completed members fetch it on mount, navigation, focus, reconnect, return to a visible tab, and every minute while visible. Overlapping passive events keep an already-running count read instead of cancelling and restarting it. Read acknowledgements and successful request decisions explicitly replace any older count read without reloading the list. Requests have a 15-second deadline; temporary count failures retain the last confirmed count. Unmounting aborts outstanding reads and stops polling. No private state is persisted locally.

Opening Activity only fetches its current page. IntersectionObserver tracks each unread item’s summary text, so a comment taller than the screen can still qualify. At least half the summary must stay on screen continuously for 250 ms. Exiting, hiding the tab, resizing, changing pages, or unmounting cancels incomplete timers; mobile navigation is excluded from the observable viewport. If the observer API is unavailable, nothing is automatically marked read. Qualified items are batched into versioned acknowledgements (up to the page size), and the badge changes after confirmed success. Failures show a status and retry with bounded exponential delay while this page remains mounted; hidden tabs pause retries. A late acknowledgement cannot clear a newer source version. No manual read button or per-type badge exists.

Navigation remembers pagination cursors; returning from a post refetches the same page, while reselecting Activity resets to the newest page. Follow decisions keep unaffected rows mounted, with remaining mutation and pagination controls disabled until revalidation completes. Rows use stable activity identities, so a changed count/version does not remount its image; visibility receipts still track the current version. Failed reads expose Retry without implying an empty page. An optional push alert opens Activity at its matching event, including older pages, after current authorization. Missing targets fall back to current activity with a status message. Acknowledgement closes matching local OS alerts through that version. See [push](../push/README.md); email activity notifications and private offline caching remain absent.

`Notifications` accepts an optional leading row, shown only on the newest page without a push focus. The member shell uses it for the [device-setup](../device-setup/README.md) suggestion, which is not a server activity item and is excluded from read receipts. `observeReadActivity` is exported for that row's badge.

Joined-invitee activity renders the whole row as a native profile link with a 64px private avatar and current handle. It uses the existing visibility dwell acknowledgement and unread badge. List/count requests opt into this event type, keeping older open clients compatible during rollout.
