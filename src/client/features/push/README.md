# Push settings

Settings offers an expandable Notifications section. `usePush` and `PushControls` implement this Settings opt-in; onboarding offers no notification step. Nothing registers, subscribes, or asks permission until the member clicks Enable notifications. Permission is requested directly in that click gesture only when it has not already been granted. Installation never asks for permission. iPhone/iPad users outside a Home Screen app see installation guidance; other unsupported browsers get a clear status. Denied permission explains how to allow it in browser/device settings. API and browser operations have bounded waits and expose retryable failures.

Alerts cover requests, new followers, comments, and likes. The permission dialog itself has no network deadline; registration starts after permission is granted. Component tests cover a delayed Android permission response with focus return and a retry after the server's temporary auth failure. They simulate browser API boundaries and do not establish real-device behavior or the cause of a production error.

The server checks the current member/session and the exact local endpoint, so isolated apps sharing a copied login cookie have independent subscriptions. Browser permission and local/server subscriptions must match before showing enabled status. Focus, visibility return, and reconnect refresh the state without prompting or polling. Changing accounts never adopts an old subscription. A failed registration can retry the same subscription created during that mounted account’s explicit opt-in, without repeating permission or subscribing again. A dismissed or blocked permission does not register. Lost local state from an earlier attempt is not treated as proof of account ownership. Disable revokes only the current endpoint’s server delivery before attempting matching browser cleanup; successful sign-out also unsubscribes locally. Server session deletion/expiration remains authoritative if cleanup fails. Stale Settings reads cannot overwrite a later enable/disable action.

`public/sw.js` only handles installation, activation, push, and notification clicks. It has no fetch handler, private cache, offline content, analytics, or silent pushes. It shows generic text without private names, comments, or images. Tapping an alert probes same-origin windows for standalone mode (bounded to 200 ms), prefers an identifiable installed window, then falls back to an existing browser window or opening the same-origin Activity route for its validated logical key; unavailable targets show a status and the current timeline. Receipt does not acknowledge activity. Existing 250 ms visibility tracking remains the only automatic read action, then closes local alerts through that acknowledged version. Other devices' delivered OS alerts are not remotely dismissed.

Node component and service-worker VM tests verify permission gestures, enabled/disabled/error/unsupported states, device guidance, safe destinations, and cleanup. Browser and visual testing are prohibited; actual device permission and OS delivery are not covered by those tests.

Browser selection remains platform-controlled when no identifiable installed window is open. The window-mode probe exchanges only a boolean, stores no data, and adds no fetch handler. Old loaded clients retain delivery but receive a reload instruction when trying to mutate the obsolete session-wide push API.
