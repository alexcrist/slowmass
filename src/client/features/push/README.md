# Push settings

Settings → Notifications starts with a This device section (`PushDevice`, built from `usePush` and `PushControls`) that shows whether push works here and walks through turning it on; on iPhone/iPad outside the Home Screen app it shows the numbered Add to Home Screen steps, ending with where to enable notifications in the installed app. the [device-setup](../device-setup/README.md) Activity row reuses `usePush` for its Turn on action. Onboarding offers no notification step. `devicePushState` reads this device's permission and local subscription and confirms an unconfirmed endpoint with the server once per page load; it only chooses which suggestion to show and never replaces `usePush`'s status. The service worker does not handle `pushsubscriptionchange`: a renewed or orphaned subscription is recovered by the Activity suggestion the next time the app is opened. Nothing registers, subscribes, or asks permission until the member clicks Enable notifications. Permission is requested directly in that click gesture only when it has not already been granted. Installation never asks for permission. Other unsupported browsers get a clear status. Denied permission explains how to allow it in browser/device settings. API and browser operations have bounded waits and expose retryable failures.

Which activity alerts this device follows the member's per-category choices in the same Settings page; likes are off by default. The permission dialog itself has no network deadline; registration starts after permission is granted. Component tests cover a delayed Android permission response with focus return and a retry after the server's temporary auth failure. They simulate browser API boundaries and do not establish real-device behavior or the cause of a production error.

The server checks the current member/session and the exact local endpoint, so isolated apps sharing a copied login cookie have independent subscriptions. Browser permission and local/server subscriptions must match before showing enabled status. Focus, visibility return, and reconnect refresh the state without prompting or polling. Changing accounts never adopts an old subscription. A failed registration can retry the same subscription created during that mounted account’s explicit opt-in, without repeating permission or subscribing again. A dismissed or blocked permission does not register. Lost local state from an earlier attempt is not treated as proof of account ownership. Disable revokes only the current endpoint’s server delivery before attempting matching browser cleanup; successful sign-out also unsubscribes locally. Server session deletion/expiration remains authoritative if cleanup fails. Stale Settings reads cannot overwrite a later enable/disable action.

`public/sw.js` only handles installation, activation, push, and notification clicks. It has no fetch handler, private cache, offline content, analytics, or silent pushes. It shows the title and body the server sends (names, event titles, and shortened comment or message text, never images or links), bounded in length, and falls back to generic text for older or malformed payloads. Tapping an alert probes same-origin windows for standalone mode (bounded to 200 ms), prefers an identifiable installed window, then falls back to an existing browser window or opening the same-origin Activity route for its validated logical key; unavailable targets show a status and the current timeline. Receipt does not acknowledge activity. Existing 250 ms visibility tracking remains the only automatic read action, then closes local alerts through that acknowledged version. Other devices' delivered OS alerts are not remotely dismissed.

Event answer and message identities are preserved in notification tags, click destinations, and read dismissal. Different event activity does not collapse into one generic tag, and acknowledging an older version cannot dismiss a newer one. Node component and service-worker VM tests verify permission gestures, enabled/disabled/error/unsupported states, device guidance, safe destinations, event key validation, and cleanup. Browser and visual testing are prohibited; actual device permission and OS delivery are not covered by those tests.

Browser selection remains platform-controlled when no identifiable installed window is open. The window-mode probe exchanges only a boolean, stores no data, and adds no fetch handler. Old loaded clients retain delivery but receive a reload instruction when trying to mutate the obsolete session-wide push API.

Push alerts supply the existing app icon plus a separate monochrome Caveat `s` badge for Android status bars. Platforms that ignore the badge keep their normal notification presentation; iPhone uses the installed app icon. Actual OS rendering still requires owner device confirmation.
