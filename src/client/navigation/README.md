# Navigation

Hash routes give the single-page client shareable profiles and browser Back/Forward behavior without a router dependency. Event sharing also accepts `/event/<token>` so the server can return title/cover-only crawler metadata. The client reads both path and legacy fragment event links; navigating to a hash destination clears the previous event path, and popstate restores path entries on Back/Forward. Route roots are keyed so forms, requests, and local state are unmounted on page changes; profile tab changes keep the profile header mounted. Private navigation remains behind the authenticated member shell.

Legacy `#requests` links resolve to Activity. `BackControl` uses labeled anchors with a shared arrow and touch target. Administrative parent links are deterministic. Post pages and other members’ profile back links use a bounded in-memory list of visited app routes, treating profile tab changes as one page and retaining the selected tab on return. Your own profile has no back control. Direct entry to a post or another member’s profile falls back to Feed; no control can navigate to an external history entry. User identities in feed cards, search, connection lists, comments, likes, and activity use profile anchors.

`#post/:id` opens a dedicated post page from a profile grid, feed photo, or Activity link. The shell replaces the parent screen completely and owns the back control. `PageHistoryProvider` remembers pagination cursors for up to 50 recently paginated feeds, profile grids, and Activity lists during the member session. Returning performs a fresh authorized read; it never restores cached private content. Reselecting a refreshable main destination clears the remembered cursors. Logout or reload also discards them. There is no browser-storage persistence or hidden mounted list.

Account setup also uses that bounded route history to return an event-only member to their latest event, or Events on direct entry. A gated destination stays in the hash while setup runs, so Finish opens the requested feature without a second destination store. Event-only members can open Find and other members’ profile previews; Request to follow uses the profile’s `/join` suffix for setup and returns to the profile on Finish without sending a request. Profile preview back links use the same bounded history as full profiles. Successful setup updates an own-profile destination and the rendered route in the same state change, avoiding a read under the released username; another member’s profile destination stays unchanged.

The member session remembers scroll offsets for up to 50 routes. Browser Back/Forward and in-app return links restore the route's last offset instantly; first visits start at the top. Restoration reapplies as the page grows during fresh reads and image loading, stops on pointer, touch, wheel, or keyboard input, and expires after 20 seconds. Shorter or unavailable content clamps to the available page height. Native history scroll restoration is disabled while the member shell owns it and restored on unmount. Hashchange/popstate pairs save the departing position only once. Reselecting a refreshable main destination clears offsets along with the remembered list state; logout and reload discard all of it.

Only navigation metadata survives a route unmount: list cursors, Find's search/shuffle seed/loaded depth, and up to 100 route-scoped post comment expansion/page states. Returning to Find sequentially refetches its previously loaded pages, adding one authorized read per page; it never restores old directory rows. Comment drafts and other unsaved form inputs are not retained. Changes to content or layout can change which item occupies a saved pixel offset. No hidden pages, cached private API responses, or browser-storage persistence are introduced.
